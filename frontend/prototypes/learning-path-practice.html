HashMap 并发扩容为什么会死循环？1.8 怎么修的？

先合上，在心里把这道题说一遍，再展开三档样例对照——这一步的自评只决定进度怎么记，不判分。
及格 · 说对现象与根因“1.7 是头插法，多线程同时扩容时链表可能被插成环，get 的时候一直找不到尾就死循环了。1.8 改成尾插法，就不会成环了。”
良好 · 讲清成环过程“两个线程同时扩容，各自持有旧链表的头。A 线程把元素搬过去后，B 线程按旧顺序继续搬，指针互相指成了环。1.7 头插法在搬移时反转了链表顺序，是成环的诱因；1.8 尾插保持相对顺序，从根上消除成环条件。”
优秀 · 指出尾插≠线程安全“补一点：改成尾插只是消除了成环这一个并发缺陷，HashMap 本身仍非线程安全，1.8 并发扩容依然可能丢数据。真要用并发场景得上 ConcurrentHashMap。面试官常拿这个收尾。”

先把"成环"这件事讲透

1.7 的 transfer 是头插：每搬一个节点，就把它塞到新桶的链头。这个动作会让链表顺序整体反转——而反转，正是两个线程交叉搬迁时把指针指成环的前提。

// 1.7 头插（简化）
e.next = newTable[i];   // 新节点指向当前桶头
newTable[i] = e;        // 当前桶头换成新节点

1.8 改成尾插，搬迁时保留相对顺序，从根上消除了成环条件。但注意：这修的是"成环"，不是"线程安全"。

还是没懂？问它
AI 即时讲解AI 生成 · 只辅导不裁决
尾插就绝对安全了吗？
不是。尾插只消除了成环，1.8 并发扩容仍可能丢数据——两个线程同时 put，一个的写入可能被另一个覆盖。要真正并发安全，用 ConcurrentHashMap：它用 CAS + synchronized 锁桶，而不是靠 HashMap 的写法来兜。所以面试里答完"尾插"最好补一句"但它仍非线程安全"，这是拉开档位的地方。
