HashMap 在 JDK 1.8 做了哪些改动？为什么引入红黑树？

面试官还可能这样问（问法变体）

谈谈 HashMap 的底层实现1.8 相比 1.7 优化了什么为什么链表要转红黑树
中级高频 78%追问 3 层资料 2 篇你的目标：练到第 2 问算够
叙述框架 · 建议按这个顺序说
1
先给结论数组 + 链表 + 红黑树，链表过长时转红黑树。
2
对比 1.7 讲改动头插改尾插，解决并发扩容死循环；扩容时索引重算简化。
3
树化条件要精确链表长度 ≥ 8 且数组容量 ≥ 64 才树化，否则先扩容。
4
收尾往上顶一层为什么阈值是 8 —— 泊松分布下概率极低，是安全垫不是性能线。
追问链 · 面试官会怎么追
第1层顺着答树化阈值为什么是 8？›
答到泊松分布即及格：哈希碰撞下单桶节点数到达 8 的概率约千万分之一，说明正常代码几乎不会触发树化。
第2层往下钻退化阈值为什么是 6，不是 7？›
留出缓冲带防止在 7、8 之间反复抖动：结构转换本身有成本，阈值错开避免频繁互转。
第3层边界压测让你重新设计扩容策略，怎么权衡？›
开放题，评估维度：内存换时间（提前扩容）、迁移成本（分批 rehash）、读多写少场景。答出权衡框架而非唯一答案。
三档回答样例 · 对照自己的说法
及格 · 结构答对，能站住"数组 + 链表 + 红黑树。链表长度超过 8 会转成红黑树，查询更快。1.8 还把头插法改成了尾插法。"
良好 · 有对比、有条件、有因果"1.8 的改动：① 头插改尾插，修复 1.7 并发扩容成环的问题；② 树化需同时满足链表 ≥ 8、容量 ≥ 64，否则优先扩容；③ 查询复杂度从 O(n) 降到 O(log n)，这是引入红黑树的原因——恶意哈希碰撞下防止性能退化。"
优秀 · 讲到设计者的取舍"在良好的基础上补：阈值 8 源自泊松分布——理想散列下单桶 8 个节点的概率约 0.00000006，树化是防御机制而非常态；退化阈值取 6 留缓冲防抖动；另外 1.8 扩容用 high/low 链拆分，免去了逐个 rehash。"

一文吃透 HashMap：从 1.7 到 1.8

先回答：为什么改？

1.7 的 HashMap 在并发扩容时可能因头插法形成环形链表，查询直接死循环 CPU 打满。1.8 改为尾插，从根上消除成环条件——这也是面试最爱追问的起点。

考点提示：回答时先讲"为什么改"，再讲"改了什么"，顺序反过来会显得背题。

树化的精确条件

树化要同时满足两个条件，缺一不可：

if (binCount >= TREEIFY_THRESHOLD - 1   // 链表 >= 8
    && table.length >= MIN_TREEIFY_CAPACITY) { // 容量 >= 64
    treeifyBin(tab, hash);              // 否则只扩容
}

容量不足时优先扩容而非树化——扩容拆桶本身就是一次"减压"。

考点提示：只说"超过 8 就转红黑树"是及格线，两个条件都说全才到良好。

阈值 8 的数学来源

理想散列下，单桶节点数服从泊松分布，到达 8 的概率约千万分之一。所以 8 不是性能线，是概率安全垫——正常代码几乎不会触发树化，触发了就说明 hash 写得有问题。
