# 考点库设计

> 企划书里说"核心资产是一个考点库"，但只有一句"每个考点长这样"。这篇文档把这块资产当真正的核心来设计：字段为什么这么定、概念之间什么区别、数据怎么存、内容怎么生产。写的时候按开发自己的库表来要求——将来是要真建表的，现在含糊一个字段，将来返工一张表。

> **v2 修订说明（2026-09-22）**：初版概念层立得住，但物理层有多处硬伤，经两轮评审（用户视角 + 架构视角）后整体改造。改动集中在四处：①承重实体缺身份（追问层没有稳定键）；②承重字段没落表（`sub_type`、层级、放弃理由、路径骨架）；③个人资产混进全局库表（复盘信号）；④DDL 不可执行、几乎无约束。改动清单见文末「修订记录」。

## 一、设计的原点：从真实面试反推

题库不是"题目 + 答案"的集合。设计之前先回答一个问题：**面试官问一道题时，他到底在筛什么？**把这想清楚了，字段自然就长出来了。

回忆真实面试，面试官的问法收敛下来就八类：

| 问法 | 例子 | 他在筛什么 |
|---|---|---|
| 概念题 | "ES 为什么是近实时的？" | 概念边界清不清楚 |
| 原理题 | "MVCC 在 InnoDB 里怎么实现的？" | 懂不懂内部机制，还是只会用 |
| 参数/实践题 | "refresh_interval 你线上怎么定的？" | 有没有真的上过线，有没有数字 |
| 对比题 | "Redis 和 Tair 你为什么选了 Tair？" | 有没有做过技术选型，还是被动接活 |
| 场景题 | "缓存和 DB 不一致你们怎么办？" | 有没有系统性思路，能不能分主次 |
| 设计题 | "设计一个短链系统" | 架构能力、拆解过程 |
| 项目追问 | "这个项目你负责哪块？为什么不用 X？" | 简历是真的还是包装的 |
| 下钻追问 | 上面任何一题的"那…呢？再往深了说呢？" | 深度边界在哪 |

同时，面试官判断一个回答好坏，心里用的也就五把尺子：**对不对（正确性）、全不全（因果链完整性）、深不深（扛追问层数）、实不实（有没有数字/案例/参数）、条理清不清（结构）**。

这 8 类问法 + 5 把尺子，反推出考点库需要的全部实体：下钻 → **追问链**；答不出往往是因为缺前置 → **前置依赖**；同主题的问题要共享讲解 → **主题簇**；5 把尺子 → **评分要点**；"对不同年限的人要求不同" → **职级要求**；"哪些题高频" → **频率信号**；"你简历写的你得能讲" → **简历授权**（这个不在库里，后面讲为什么）。

**注意：8 类问法本身不直接变成分类字段。**概念题、原理题、参数题、对比题的练习循环和字段结构高度重合（判据见 2.6），把它们切成七个枚举值只会制造维护成本。这节的分析是推导工具——它负责推出上面那些实体，推出之后功成身退；真正落到库里的分类是「题型」，按"练习循环不同 + schema 不同"切出来（见 2.6）。

**设计原则只有一条：库里存的是"面试怎么问、怎么判"的结构化知识，AI 只做对齐。**凡是能预判的都不让 AI 现场编。

## 二、核心概念定义与区别

这些概念两两长得像，逐对给出定义和**判断标准**——将来标定题库时按标准走，不靠感觉。

### 2.1 考点 vs 追问层

- **考点**：能独立成为一道面试题的原子知识单元。"ES 近实时写入"是考点，"倒排索引"是考点。
- **追问层**：同一考点内的深度切片，主问题答完后的连续追问，没有独立语境。

**判断标准：这条内容能不能脱离主问题单独被问出来？**"translog 设 request 还是 async"——单独问出来它就是一道题，但它离开主问题就没有语境，且永远在主问题答完之后才被问，所以它是追问层。"倒排索引是什么"可以随时单独被问，所以是独立考点。

**为什么这个标准重要**：如果把追问层拆成独立考点，前置依赖图会被"同一件事的三层"污染——要么出现循环依赖，要么路径生成把一条追问链排成三个考点让用户重复练。追问层**有序、整体读写、由主问题锚定**，这三个特征决定了它是考点的内嵌结构，不是库里的独立实体。

**但"内嵌"不等于"没有身份"**（v2 修正）：追问层是承重实体——判定、评分、报告、历史对比全都指向"第几层"。所以每层必须有**稳定键 `layer_key`**（如 `l0` 主问题、`hotspot`、`capacity`），而不是靠数组下标对齐。层序可以重排、内容可以校对，`layer_key` 不变；完整规则见 2.12。

### 2.2 主题簇 vs 前置依赖

两个维度长得像，实际完全正交：

- **主题簇**是**组织维度**：内容生产单位。"从零讲"按簇写一篇共享（RocketMQ 十个簇共享十篇讲解，而不是一百个考点写一百篇），簇内考点主题相近。
- **前置依赖**是**学习维度**：先懂什么才能懂这个。"分片规划"属于"分片与集群"簇，但前置是"倒排索引"——依赖可以跨簇。

主题簇还是**完美答案的挂载点**：设计演进链的簇挂 `reference_solution`——完整参考架构 + 核心伪代码，即面试官手里那份理想答案；演进链每层的 expect 都是从它按条件切片拆出来的，评分要点按它标深度等级。知识点簇不挂它（八股的"完美答案"就是各考点的叙述框架）。

**完整答案的展示规则**：学习态随时可看——考点详情里有「看完整答案」入口，点开摊开全部解法和伪代码，看的人自己决定：觉得太简单可以不看，觉得太高深看了留个印象，看不懂就沿前置回退。进合卷练 / 复测 / 模拟考时，完整答案随资料一并收起（闭卷机制不变，不存在拿它作弊的口子）。簇内多个考点共享同一份 reference_solution，一处维护，改一处全簇生效。

类比：**簇是包结构，前置是调用依赖**。包内聚是给生产和维护看的，依赖关系是给学习路径排序看的。每个考点挂且只挂一个主簇（真跨簇的选主簇挂）——**这是有损取舍**：跨域题（Redis 缓存 + ES 一致性）的次要归属表达不了，用前置跨域引用补偿。前置可以 0~n 个（多数 0~2，别硬凑链条凑成图）。

### 2.3 难度 vs 职级要求

- **难度**：这个东西**学起来多难**——决定学习路径里排在第几周。
- **职级要求**：面试官**会问多深**——决定追问下钻的停止点和判定标尺。

同一考点，对 3 年候选人难度高，对 8 年候选人难度低——但面试官对 8 年的下钻也更深。**两个维度独立存储，互不推导**。混在一起的下场：路径排序被面试标准绑架，5 年的人被按 8 年的深度排路径，前两周全是劝退题。

职级要求不存"每级一套评分要点"（维护爆炸），存**每级的差异描述 + 下钻停止点**，判定时和评分要点合并使用：

```json
"不同职级的要求": {
  "中级": {"差异": "讲清 refresh 和 Translog 各自的职责", "钻到第几层": 1},
  "高级": {"差异": "说清写入吞吐和可见延迟的取舍", "钻到第几层": 2},
  "资深": {"差异": "拿压测数据讲生产上怎么选", "钻到第几层": 3}
}
```

**下钻停止点必须对用户可见**（v2 新增）：`level_expect` 现在只做判定标尺——用户不知道"讲到什么程度算够"，练的时候只有焦虑没有目标。学习卡片和模拟考报告都要把"你这个年限，讲到第 N 层算够"渲染出来，让它成为练习时的**目标刻度**而不是隐藏的评分标准。同一份数据，判定器读它做停止判断，前端读它做目标提示。

### 2.4 题面 vs 问法变体

- **题面（title）**：主问法，用户在卡片上看到的。
- **问法变体（variants）**：同一考点的其他问法数组，预存 2~3 条 + AI 可在评分要点范围内现场改写。

**为什么必须存变体**：追问链全透明后，背链子就能应付按原文问的 AI。"链子是骨架不是剧本"靠两个数据支撑——预存变体（每次抽一条）+ 现场改写（rubric 内）。变体是数据字段，改写是生成策略，两者配合。

### 2.5 从零讲 vs 叙述框架

- **叙述框架（core_answer）**：给"大概懂但讲不完整"的人做回忆结构，挂在考点上。
- **从零讲（explainer）**：给完全没底层的人从"这个技术为什么存在"讲起，几百字一篇，**挂在主题簇上，簇内共享**。

区别的本质是**假设的读者起点不同**，共享粒度也不同：框架必须逐考点定制，讲解可以按簇量产（每簇一篇 1500 字，人工校的量可控）。**从零讲只有一个来源——`kp_cluster.explainer`**（v2 修正：初版样板在考点 `detail` 里又塞了一份同名"从零讲"，违反"一处维护"，样板自己踩了自己的规则）。考点确需补充时，用独立字段名「补充说明」，不与簇级讲解同名、不同源。

### 2.6 题型：按什么分类，什么时候才配新增一类

分类必须有意义：**展示交互上走得不是同一条流程，或字段结构长得不一样**——满足其一才值得分一类；两条都不满足的分类是噪音，是纯粹的维护成本。

**新增题型的门槛就这两条**：

1. **练习循环不同**：用户看到的界面、走的步骤不一样；
2. **schema 不同**：需要的字段结构不一样（内容单元、评分标尺、脚手架不同）。

**最终决策（v2 定稿）**：题型字段统一为 **`sub_type`**（`kp_type` 这个恒为「知识点」的单值列已删除），取三个值：

| sub_type | 练习循环（交互） | 字段结构（schema） | 评分标尺 |
|---|---|---|---|
| `default`（默认八股） | 看资料 → 追问 → 合卷练 → 隔天复测 | 追问链 + 分级评分要点 | 四档规则 |
| `design_chain`（设计演进链） | 同循环，追问链语义 = 条件升级 | 演进链各层 + 按层 rubric + 簇级 reference_solution | 按层命中 + 深度分布定位 |
| `narrative`（项目叙事） | 看标准故事 → 合卷讲 3 分钟 → 隔天复测 | core_answer = AI 起草的标准故事（六要素、用户确认事实）+ 用户实例故事挂 user 态 | 指标清单全命中：数字 / 冲突 / 3 分钟收住 |

> **为什么不是初版的 kp_type + sub_type 双层**：`kp_type` 收敛后只有一个取值，是个零信息量的伪字段；真正的分流开关是后者。v2 直接让 `sub_type` 承担题型语义，DDL 里加 CHECK 约束（见 4.3）。
>
> **预留**：`sub_type` 现在把"内容归属（预制 vs 用户私有）"和"追问链语义（下钻 vs 条件升级）"两个正交维度压成了一个枚举。当前三个值够用；一旦出现「用户私有项目叙事 + 条件升级追问」这类组合（真实设计面很常见），就把 `sub_type` 拆成两条独立轴——这是已知的演进点，不是当前缺陷。

**面试问法的八类与题型的关系**：概念题、原理题、参数题、对比题、线上小场景、下钻追问——这些**不是题型**，它们全部走 `default` 的循环和字段结构。它们影响的是字段的**内容**，不是字段的**结构**：

| 面试问法 | 归属题型 | 落到哪些字段的内容里（结构不变） |
|---|---|---|
| 概念题 / 原理题 | default | 叙述框架的写法（是什么 → 为什么 → 怎么实现） |
| 参数 / 实践题 | default | 追问链里出现"线上怎么定"层；评分要点的具体性要求 = 必须给参数名 |
| 对比题 | default | 追问链里放对比层（"为什么不用 X"）；常见错误里放混淆点 |
| 线上小场景题 | default | 追问链里放排查思路层；案例锚点挂个人事故复盘 |
| 下钻追问 | default | 就是追问链本身，不独立存在 |
| 设计题 | design_chain | 演进链各层条件升级：估算 / 热点 / 一致性 / 容灾 / 取舍（见 2.7） |
| 项目追问 | narrative | 六要素组织的标准故事（AI 起草、用户确认）+ 个人案例锚点 |

同理给将来标题库的人一条防线：想标"记忆型 / 理解型 / 应用型"这类分类时，先过两条门槛——循环一样、字段一样，就不配成为题型，最多是一个 tag（而 tag 也只在它参与排序或筛选时才值得存）。**每个枚举值背后是一套新练习循环 + 一套新评分模板 + 原型里一套新界面**，三倍维护成本，没有交互和结构差异的枚举值就是在白付这个成本。

**项目叙事的统一（v2 修正）**：叙事的"标准答案"由 AI 根据建档对话收集的项目素材起草——按六要素组织（背景 / 目标 / 方案 / 冲突 / 结果带数字 / 复盘），六要素从交互层降为标准故事的组织结构。生成时守住一条红线：**AI 只组织不编造**，故事里每个数字和事实逐条经用户确认后才生效。

**关键修正——用户故事不进全局库表**：初版说"确认后成为该叙事考点的 core_answer"，但 `core_answer` 是全局 `kp_main` 的列，写进去就意味着"每个用户一条全局考点"，直接违反第三节的库/态分离。v2 的处理：

- `kp_main.core_answer` 对 narrative 存的是**六要素模板**（组织骨架，全局一份，可预制）；
- 用户的**实例故事 + 逐条事实确认记录**存在用户态新表 `user_narrative`（见 4.11）；
- 事实确认是 narrative 独有的状态机（确认状态 / 确认时间 / 逐条记录），有独立生命周期，必须落表——初版遗漏。

确认后练习循环完全复用知识点模式，评分退化为一张简单指标清单：数字给没给 / 冲突讲没讲 / 3 分钟收没收住，全部必须命中——你的项目，你就要全部答到。叙事的定位由此收敛为**打磨工具而非训练系统**：AI 负责把故事组织好、话术磨好、提醒你补数字；用户负责确认事实、练熟、内化。这是"每个用户内容都独一无二、无法预制"的题型唯一诚实的做法，维护成本压到零。

题型特有字段放 JSONB 扩展（见存储方案），不为每种题型建独立表——查询模式是"按考点拉详情"，不是"跨考点找某种题型的某字段"。**但 `sub_type` 本身是实列**（有 CHECK、要索引），因为它是判定/调度/渲染三条管道的分流开关，属于控制面，不能降格进无约束的 JSONB。

### 2.7 场景设计需要独立题型吗：演进链方案（最终结论）

初版设计给场景设计立了独立题型（五步脚手架 + 平行三板斧 + 维度计分），论证了四点"不可通约"。后来被一个反问击穿：**为什么不能把设计题做成演进链？**

演进链方案：

- **主问题**：设计百万并发商品详情系统；
- **第 1 层 · 最简版**：一台 DB 一台缓存跑起来——动手前先问约束。最简版考的是"不过度设计"的判断力；
- **第 2~5 层 · 条件升级**：QPS 10w 哪里先崩（逼出量级估算 + CDN + 多级缓存 + 静动态分离）→ 大促热点打满单分片（热点探测 + 散片）→ 改价 5 秒可见（binlog 失效链）→ 缓存集群整体挂了（有损降级）——**每层条件升级，逼出一个高端方案**；
- **第 6 层 · 复盘取舍**：为什么不用 X，理由必须成立；
- **知识簇 = 各层 expect 合起来的完美答案**——内容生产按层走，不用另起炉灶。

当初四论据的重新检验：

1. **时间的形状**：合卷练时长参数化后，"全链连讲 20 分钟"就是一场浓缩设计面——耐力训练不丢，反而**多出渐进式碎片练习**：每层 5 分钟、从最简版起步，新手也能下嘴。这是独立题型做不到的；
2. **评分塑造行为**：演进链每层有 expect 要点 → 按层要点命中 → 四档规则直接复用，维度计分取消。评分体系全题型统一，"练歪"风险消失——每层逼出的恰好是正确行为（先澄清、先算账、再升级）；
3. **答案所有权**：不涉及场景题（那是项目叙事的论据）；
4. **修复路径**：前置回退照常，且打通得更彻底——第 3 层"热点打满"的前置就是知识点"缓存击穿"。

初版方案的剩余价值全部收编：平行三板斧 → 编入链的高层（线性化），模拟考乱序抽层保拟真 + 防背题；澄清边界 → 第 1 层 expect 内含 + 模拟考里 AI 沉默等反问。

**最终结论：`sub_type` 只有三个值——`default` / `design_chain` / `narrative`，其中演进链与追问链结构同构（都是有序递进层），区别只在语义：条件升级 vs 深度下钻。**2.6 的判据（循环不同 / schema 不同才配分题型）经受住了检验——恰是它杀掉了第三个题型。（后记：项目叙事随后也走了同一条路——AI 标准故事 + 事实确认后并入知识点模式，只是把用户故事挪进用户态，见 2.6。）

### 2.8 评分要点分级制：没有银弹的题怎么判

八股有客观对错：refresh 管可见说成落盘就是错——"必须命中 + 加分项"够用。但设计演进链的很多要点没有银弹：本地缓存选 Caffeine 还是 Guava、静动态分离切在哪里，都是取舍不是对错。硬套"必须命中"会变成背答案。

所以评分要点升级为**分级制**——每个要点标 `level`：

- **基础**：答出算撑住这一层（缓存分层、读写路径）；
- **中级**：想到算良好（binlog 失效链路、静动态分离）；
- **资深**：**想到加分，不想到不扣**——没有银弹的取舍全放这级（本地缓存选型依据、有损服务的边界、反问约束条件）。

档位由命中要点的**深度分布**决定：基础全中 = 及格；+ 中级 = 良好；+ 资深 = 优秀。从"命中率"变"深度定位"——你在完美答案的坐标系里被定位，而不是被一张标准答案的清单打叉。

这个分级其实是"不同职级的要求"字段的评分化：职级要求说"资深要能拿压测数据讲"，分级制把它落成"带压测数字的要点 = 资深级，命中即加分"。两个字段合流，判定时一次对齐。

**评分要点必须可判定**（校正环节的硬门槛）："讲得有条理"LLM 判不出来，"给出参数名"判得出来。不可判定的要点在校对时必须改写成可判定的表述——这是校对里最容易漏的一环。

**命中要点的快照必须带 `layer_key` 和 `level`**（v2 修正）：初版只说"存要点文本快照"，但档位由深度分布决定，而深度挂在层上——不存 `layer_key`，rubric 一改历史判定就既不可解释、也不可比。快照三件套：`layer_key + level + 要点文本`。

### 2.9 追问的方向分组与覆盖保证

一个答案之后常有几个**平级追问方向**（容量 / 一致性 / 容灾）——追问链的线性排列会丢掉"这是三个平行方向"的信息，也引出一个真问题：模拟考抽了热点方向，一致性和容灾这次没问到，知识点遗漏了吗？

机制定死三条：

1. **每层标 `dir`（所属方向）**：同方向的层按序排列，方向之间平级；
2. **模拟考横向轮转遍历**：第一轮每个方向问一层（扫广度）；判定发现「缺/错」的方向，第二轮纵向加深（打弱点）——先横切再纵深，正是真实面试官的行为；
3. **覆盖保证**：时间不够没扫到的方向标"未覆盖"，进下次抽查优先队列——**任何方向都不会因为这次选了别的方向而丢失，只会在时间窗口内延后**。覆盖度（覆盖方向数 / 总方向数）进模拟考报告。

**方向状态必须落表**（v2 修正）：初版的 `user_kp_state` 粒度是 `(user_id, kp_id)`，到不了方向维度，"未覆盖方向进优先队列"这句承诺**没有表承载**。v2 新增 `user_dir_state`（见 4.12），粒度 `(user_id, kp_id, dir)`，存覆盖标记与抽查优先级。

### 2.10 频率信号：明细与聚合分开

"这题高频吗"不是一个数字，是多个来源的证据：

- **面经信号**：爬面经时记"出现次数、来源岗位、有没有追问记录"——只取信号不抄正文；
- **复盘信号**：用户真实被问到的题（权重最高，且随面试次数累积——这是"知彼"个人化的核心资产）；
- **人工标定**：AI 判断不了的，手动定。

**库级信号与个人信号必须分开存**（v2 修正）：初版把"面经/人工"（全局内容资产）和"复盘"（个人隐私资产）塞进同一张无 `user_id` 的表——文档自己承认这是"库内容预制、信号持续累积的交界处"，却当成一张表处理，直接违反第三节的库/态分离。v2 拆为：

- `kp_freq_signal`：**库级信号**（面经 / 人工），全局一份，可公开；
- `user_kp_signal`：**个人复盘信号**（带 `user_id`、关联真实面试场次），每人一份，属隐私资产。这样"目标公司最近在问什么"这种个人时间序列才取得到，内测第 2 个用户进来也不会被污染。

**聚合分口径统一（v2 修正，消解初版自相矛盾）**：初版 §2.10 写"主表物化一个聚合分"，§4.4 又写"不落列在 kp_main、先不物化"——两处对着干。定稿：**聚合分不落主表**（落表会被误当唯一真相），先查询时实时 `group by`（几百个考点足够快）；库到万级、聚合成热路径时，再引入独立汇总表 `kp_signal_agg`，绝不回填进 `kp_main`。

为什么明细不能丢：聚合分丢了来源就没法解释"为什么这题排前面"，而且复盘信号的时间序列本身就是价值（目标公司最近在问什么）。

### 2.11 考点状态机

```
draft（AI 生成）→ reviewed（人工校过）→ active（可进用户路径）
                                          ↘ retired（被合并/废弃，保留历史）
```

**没校过的内容不许进用户路径**——AI 生成的技术内容没人工兜底，JVM 参数错一个就是害人（企划书原文）。

**v2 两处修正**：

1. **补 `active → retired` 转移**：初版状态图把 `retired` 只画在 `reviewed` 之下，但真正会被废弃的是正在用的 active 考点。同时 retired 的考点带 `superseded_by`，标明"被合并到哪条"，供在途用户态迁移（见 4.13）。
2. **状态机必须覆盖簇级内容**：初版 `kp_cluster` 只有 `created_at`、没有状态机，但它挂的 `explainer` / `reference_solution` 是**直接给用户看的**——"没校过不许进用户路径"这条安全线漏了簇。v2 给 `kp_cluster` 补 `status` / `reviewed_at`，安全线扩到簇级。

### 2.12 追问层身份与编号基准（v2 新增）

追问层是承重实体，但初版没有任何稳定标识，全靠序号对暗号，而且**三套基准并存**：`followups` 里 1-based（"层": 3）、`answer_log.layer_no` 里 0-based（`{"seq":2}`）、原型数组 0-based。校对重排一层，历史判定全体错位——产品核心指标"断在第几层""扛几层追问"随内容校准而漂移。

**规则定死三条**：

1. **每层一个稳定 `layer_key`**：主问题固定 `l0`；其余层用语义键（`capacity` / `hotspot` / `consistency` / `dr` / `tradeoff`）。`layer_key` 是层的身份，永不复用、永不改。
2. **`layer_key` 贯穿三处**：`followups[].layer_key`、`rubric.按层要点[].layer_key`、`answer_log.layer_key` 全部引用同一个键；数组序号只作**展示排序**，禁止作身份。
3. **判定快照按 `layer_key` 存**：`verdict` 里记录 `layer_key + level + 要点文本`，rubric 改动只影响未来、历史始终可解释可比。

### 2.13 答况"空"与"错"的可纠正边界（v2 新增）

企划书的答况四分流里有个**"空"（没答上来）**，但初版 `answer_log.answer_text` 是 `not null`——"空"没有自然表达，只能约定塞空串。v2 修正：`answer_text` 允许 null，另加 `is_blank` 标记显式区分"空答"。

另一个矛盾：单考点规则说"出现『错』即不及格"（硬否决），模拟考流程又说"温和教练纠正后同层变体再问一次"——**同一场里既判死又给重来机会，两处打架**。v2 划清边界：

- **硬否决的"错"**：概念反了/混了（refresh 说成落盘），照旧判死、记 `fail`；
- **可纠正的**：表达瑕疵、口误、语音转写错误——走 `answer_log.appeal`（none / requested / accepted / rejected），用户可申诉，`accepted` 后该次判定降级为"不计入档位"；模拟考的"同层变体再问一次"结果**覆盖**原判定，而不是并列两条 `fail`。

## 三、最重要的架构决策：库与态分离

**考点库（kp）= 全局内容资产，一份，人工校准；用户态（user_*）= 每个用户各自的状态，随练习持续变化。**两条线，两种生命周期。

v2 把"态"从初版的单表扩展为一组表，但边界原则不变：**全局可公开的进 kp_*，个人私有的进 user_***。

用户态承载（初版只写了 4 项，v2 补齐归属与落表）：

- **画像**（`user_skill`）——逐条拍板的技能清单，按技能域粒度；
- **计划**（`user_plan`）——目标岗位、JD、备考周期、每日时间预算；
- **路径骨架**（`user_path`）——顺序 + 层级（底线/主攻/放弃）+ 放弃理由 + 授权来源；
- **练习状态与调度**（`user_kp_state`）——五态 + SM-2；
- **我的私有内容**（`user_kp_private` / `user_case` / `user_narrative`）——备注话术、个人案例、叙事实例故事与事实确认；
- **方向覆盖**（`user_dir_state`）；
- **作答与判定历史**（`attempt` / `answer_log`）——答案资产库；
- **个人复盘信号**（`user_kp_signal`）。

为什么必须分：

1. **复用**：内测 5~10 人时，库只有一份，每人各自的态。混在一起，第二个用户进来就得洗数据；
2. **更新安全**：库校对、加变体是内容操作，不该碰用户进度；用户练到 done 也不该锁死内容更新；
3. **隐私与备份策略不同**：答案留档、个人案例、复盘信号是用户隐私资产，内容资产是可公开的库——将来真有商业化念头时，这一步决定你能不能睡得着；
4. **重置语义清晰**：换目标岗位重开画像，态按授权来源重建，库原地不动。

**两个特例必须显式标注**（v2 新增，避免后人误判为设计疏漏）：

- **`kp_freq_signal` 不含个人信号**：个人复盘信号在 `user_kp_signal`。库级与个人级信号物理隔离，是这套分离的一部分，不是遗漏。
- **`user_narrative` 与 `kp_main.core_answer` 的分工**：库侧只放六要素模板，用户故事放用户态。"每个用户独一无二的内容绝不进全局库表"是硬约束。

## 四、数据模型与存储

### 4.1 实体关系

> 本节 DDL 为 PostgreSQL 口径（`jsonb` / `timestamptz` / `check`）。实际落地 **SQLite** 的方言改写（`TEXT` 存 JSON、ISO8601 存时间、`INTEGER PRIMARY KEY AUTOINCREMENT`、外键需连接串显式开启等）见 [系统架构设计](系统架构设计.md) 6.2；SQLite 原生支持 CHECK 与 JSON 函数，PostgreSQL 里写的 CHECK 语义可原样保留。

```
skill_domain 1 ──── n kp_cluster
skill_domain 1 ──── n user_skill
kp_cluster   1 ──── n kp_main
kp_main      n ──── n kp_main         通过 kp_prereq（只存"我的前置"）
kp_main      1 ──── n kp_freq_signal  （库级信号：面经 / 人工）
kp_main      1 ──── n kp_candidate    （候选池，映射后可空）

app_user     1 ──── 1 user_plan
app_user     1 ──── n user_skill      （画像：用户拍板的技能清单）
app_user     1 ──── n user_path       （路径骨架：顺序 + 层级 + 授权来源）
app_user     1 ──── n user_kp_state   （练习态：状态 + SM-2 调度）
app_user     1 ──── n user_kp_private （我的：备注 / 收藏）
app_user     1 ──── n user_case       （个人案例 / 故事素材）
app_user     1 ──── n user_narrative  （项目叙事实例故事 + 事实确认）
app_user     1 ──── n user_dir_state  （方向级覆盖与抽查优先级）
app_user     1 ──── n user_kp_signal  （个人复盘信号）
app_user     1 ──── n attempt 1 ──── n answer_log

kp_source_doc 1 ──── n kp_candidate   （一份素材拆出多道候选题）
```

**建表顺序**（v2 补：下面是依赖安全的 DDL 执行顺序，照此建表不会因 FK 引用未建的表而失败）。注意文档按**逻辑分组**排列表，与**物理建表顺序**不同，`kp_cluster` 必须先于 `kp_main`：

```
1. skill_domain
2. kp_cluster            （FK → skill_domain）
3. kp_main               （FK → kp_cluster、自引用 superseded_by）
4. kp_prereq             （FK → kp_main）
5. kp_freq_signal        （FK → kp_main）
6. kp_source_doc         （无 FK，v3 补）
7. kp_candidate          （FK → kp_main、kp_source_doc）
8. app_user
9. user_plan             （FK → app_user）
10. user_skill           （FK → app_user、skill_domain）
11. user_path            （FK → app_user、kp_main）
12. user_kp_state        （FK → app_user、kp_main）
13. user_kp_private      （FK → app_user、kp_main）
14. user_case            （FK → app_user、kp_main）
15. user_narrative       （FK → app_user、kp_main）
16. user_dir_state       （FK → app_user、kp_main）
17. attempt              （FK → app_user）
18. answer_log           （FK → attempt、app_user、kp_main）
19. user_kp_signal       （FK → app_user、kp_main、attempt）
```

> `kp_main.superseded_by` 是自引用，建表语句内即可声明，无需拆 ALTER（指向的行在后续插入，不违反 FK）。

### 4.2 技能域字典

初版 `skill_domain` 是两处自由 `text`（`kp_main` 与 `kp_cluster`），与"用户拍板过的技能清单"之间没有任何一致性约束——用户删掉某技能后，该域考点怎么办，无答案。v2 提为字典表：

```sql
create table skill_domain (
  id         text primary key,          -- s1..s8，与原型 skills.id 一致
  name       text not null,             -- 搜索引擎与检索架构
  short      text,                      -- ES / Lucene
  sort_no    int not null default 0,
  created_at timestamptz not null default now()
);
```

簇与画像（`user_skill`）都引用它，域从此只有一处定义。

### 4.3 考点主表

```sql
create table kp_main (
  id            text primary key,                 -- 业务 ID：{簇}-{slug}，见 4.3 说明
  slug          text not null,                    -- 簇内唯一片段
  cluster_id    text not null references kp_cluster(id),
  sub_type      text not null default 'default'   -- 题型：default | design_chain | narrative
                check (sub_type in ('default','design_chain','narrative')),
  title         text not null,                    -- 主问法
  status        text not null default 'draft'     -- 状态机见 2.11
                check (status in ('draft','reviewed','active','retired')),
  superseded_by text references kp_main(id),      -- 被合并/替代去向（retired 时）
  difficulty    smallint not null check (difficulty between 1 and 5),
  core_answer   jsonb not null,                   -- 叙述框架：有序要点数组；narrative 存六要素模板
  variants      jsonb not null default '[]',      -- 问法变体数组
  followups     jsonb not null default '[]',      -- 追问链（含 layer_key / dir / seq / q / hint / expect / stop_if）
  rubric        jsonb not null,                   -- 评分要点（要点带 layer_key + level + 三档标准回答样例）
  level_expect  jsonb not null default '{}',      -- 职级差异 + 各级下钻停止点
  detail        jsonb not null default '{}',      -- 题型特有扩展
  meta          jsonb not null default '{}',      -- 来源、校对人
  reviewed_at   timestamptz,                      -- 人工校对时间
  review_due    date,                             -- 下次内容复核到期（技术结论会过期）
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now(),
  unique (cluster_id, slug)                       -- 去重的 DB 层兜底
);
create index idx_kp_cluster on kp_main (cluster_id);
create index idx_kp_status  on kp_main (status);
```

字段逐个说清楚设计意图：

- **id 用业务 ID 不用 uuid**：文档和对话里要直接引用（"es-write-nrt 这条"），跨环境迁移（我本机 → 内测服务器 → 将来）主键稳定不冲突。生成规则 `{簇}-{slug}`，**`unique (cluster_id, slug)` 是真正的去重兜底**（v2 修正：初版声称"唯一约束兜底"，但 DDL 里只有 PK、`slug` 也不是列，这条生命线其实纯靠人工纪律）；
- **`sub_type` 取代 `kp_type`**：初版 `kp_type` 恒为「知识点」是伪字段，真正的分流开关是子类型。v2 直接以 `sub_type` 为题型字段并加 CHECK（控制面字段必须有约束，不能藏进 JSONB）；
- **`difficulty` 用 1~5 整数不用易/中/难**：路径排序需要粒度，三档会造成大片并列导致顺序随机。标定规则同时给死，防标定漂移：1 = 一句话答清（"什么是索引"）；2 = 要分点（缓存三兄弟的区别）；3 = 要讲机制和取舍（refresh/flush/translog）；4 = 要给参数和线上决策依据（线程池定参过程）；5 = 要压测数据或源码级理解（translog durability 压测）。场景演进链的锚：2 = 单组件方案；3 = 多组件协作设计；4 = 演进链推进到中段（第 3~4 层）接得住；5 = 全链接住且带真实大促数字。**标定规则比标定值重要**——值会漂，规则不会；
- **`followups` 用 JSONB 数组不建子表**：判断依据是读写模式——追问层按考点整体读写、加载详情时一次全拿。但**层必须有稳定键**（见 2.12），且 JSONB 结构由成稿管道用 JSON Schema 校验（见第五节），防 AI 生成时键名漂移；
- **`rubric` 的要点分级制**：每个要点带 `layer_key` + `level`（基础 / 中级 / 资深）。八股题型：基础级 = 必须命中，资深级 = 加分项——"必须命中 + 加分项"就是分级制的特例；设计演进链：全部要点分级，**档位由命中要点的深度分布决定**（见 2.8）；
- **`core_answer` 是有序要点数组不是一段话**：它同时喂三个消费方——用户看的叙述框架、LLM 判定的对齐目标、报告生成的"你讲到了第几点"。一段散文没法按点对齐；
- **`stop_if`（追问停止条件）**：每层追问带一个"什么情况停止下钻"的说明，供判定决策参考。没有它，AI 只能靠感觉决定"还钻不钻"；
- **`review_due` 是新增的**（v2）：技术结论会过期（ES / JVM 版本变了），只有 `updated_at` 无法触发内容复核。到期的考点进人工复核队列，避免用户一直练过时答案；
- **删掉了 `skill_domain`**（v2）：考点只挂一个主簇，域可由 `cluster_id → kp_cluster.skill_domain` 推导，两处冗余必改出不一致。路径分组按簇域走。

### 4.4 主题簇表

```sql
create table kp_cluster (
  id                 text primary key,
  skill_domain       text not null references skill_domain(id),
  name               text not null,
  explainer          text,          -- 从零讲，簇内共享（唯一来源，见 2.5）
  reference_solution text,          -- 完美答案：完整参考架构 + 核心伪代码（设计演进链簇挂）
  status             text not null default 'draft'   -- v2：簇级内容也要过状态机
                     check (status in ('draft','reviewed','active','retired')),

  updated_at         timestamptz not null default now()

```

它挂两个内容字段——`explainer`（从零讲，簇内共享）和 `reference_solution`（**完美答案：完整参考架构 + 核心伪代码**）。后者是设计演进链簇的镇簇之宝——面试官手里那份理想答案，演进链每层的 expect 都是从它切片拆出来的，评分要点按它标 level；学习态考点详情直接引用渲染「看完整答案」入口（簇内共享，一处维护）；知识点簇不挂它。**新增 `status`**：这两个字段直接给用户看，必须和考点一样"没校过不进用户路径"。

### 4.5 前置依赖表

```sql
create table kp_prereq (
  kp_id     text not null references kp_main(id),   -- 这个考点
  prereq_id text not null references kp_main(id),   -- 它的前置
  primary key (kp_id, prereq_id),
  check (kp_id <> prereq_id)
);
create index idx_prereq_reverse on kp_prereq (prereq_id);
```

三条规则定死：

1. **只存"我的前置"方向，后置永远反查**——`select kp_id from kp_prereq where prereq_id = ?` 就是后置。双向冗余必改出不一致（任何关系变更都要双写）。什么时候才值得物化后置——库到万级且反查成了热路径。几百个考点的库，反查是毫秒级，不值得；
2. **写入时校环**：前置关系必须是 DAG。插入关系前沿"前置链"向上游走一遍，遇到自己就拒绝。**校环必须放在一个事务里**（v2 修正）：初版的"读—检查—写"是应用层 R-C-W，并发插入 `A→B` 与 `B→A` 可同时通过校验形成环，而 `check (kp_id <> prereq_id)` 只挡自环。做法：把校验和插入放进同一事务（必要时串行化隔离），或 DB 层用触发器 + 递归 CTE 兜底。环一旦入库，路径生成会把一条链排成循环；
3. **反向索引建在 prereq_id 上**：最高频的反查就是"这个考点的后置是谁"（路径视图里"学完这个，接下来解锁什么"）。

### 4.7 候选池

初版管道反复提"映射不上的进候选池"（内容管道起点、复盘录题的落点），但**没有表**，`status='draft'` 的语义是"AI 生成待校"，与"采集到未成稿"不是同一件事。v2 补上：

```sql
create table kp_candidate (
  id          bigserial primary key,
  raw_title   text not null,                        -- 采集到的原始题面
  raw_source  text not null
              check (raw_source in ('面经','复盘','人工','开源仓库')),

```

`doc_id` 关联 `kp_source_doc`，起两个作用：一是**溯源**（这道题是从哪份素材拆出来的，回去核对原文）；二是**避免重复拆题**（同一份文档重复调拆题接口时，已拆过的题可识别出来）[Expert judgment]。

### 4.7.1 素材文档表（v3 补）

题库素材有 pdf / doc / docx / md 多种格式，靠上传获得，需要记录"这份文件解析成了什么、拆题拆了没有"。它也是建档简历解析的落点（简历同属"上传的文档"），所以按**通用文档**建模，不叫"题库素材" [Expert judgment]。

```sql
create table kp_source_doc (
  id           text primary key,                 -- 业务 id，如 doc-20260922-001
  file_name    text not null,                    -- 原始文件名
  file_path    text not null,                    -- 本地存储路径（文件不入库）
  file_size    bigint,                           -- 字节数
  source_type  text not null
               check (source_type in ('pdf','doc','docx','md','txt')),
  purpose      text not null default 'kb'
               check (purpose in ('kb','resume')),   -- kb=题库素材；resume=简历
  parsed_text  text,                             -- 抽取出的纯文本（null=未解析）
  page_count   int,
  parse_status text not null default 'pending'
               check (parse_status in ('pending','parsed','failed','scanned_unsupported')),
  split_status text not null default 'none'
               check (split_status in ('none','split','skipped')),
  warnings     jsonb,                            -- 解析告警：疑似错行、空页等
  created_at   timestamptz not null default now()
);
create index idx_doc_purpose on kp_source_doc (purpose, parse_status);
```

三处设计说明：文件**不入库**只存路径，几百份 PDF 放 `BLOB` 会让备份臃肿、查询变慢；`purpose` 区分题库素材与简历，让同一张表服务两处消费方；`parsed_text` 在 PG 下用 `text`（无长度上限），**落 SQLite 时同样用 `TEXT`（无长度上限，无需改）**——这一点比 MySQL 省事：MySQL 的 `text` 上限 64KB，一份长面经会超、须改 `longtext`，SQLite 没这个限制 [Expert judgment]。

### 4.9 用户路径骨架

产品核心产物是**个性化路径骨架**（企划书：选几百个考点、按难度排好顺序、三层结构），但初版 ER 里没有 path 实体，原型里的 `order` 是**全局顺序**而非"每人一份"。v2 补上，并把"层级 + 放弃理由 + 授权来源"统一落在这里：

```sql
create table user_path (
  user_id      text not null references app_user(user_id),
  kp_id        text not null references kp_main(id),
  seq          int  not null,                     -- 该用户路径内的顺序
  layer        text not null check (layer in ('baseline','main','drop')),
  drop_reason  text,                              -- 放弃理由（卖点本身，必须可存）
  auth_source  jsonb not null default '[]',       -- 可多值：["简历","JD","底线层","手动"]
  weight       numeric,                           -- 授权权重（由 layer × auth_source 推导，物化便于排序）
  generated_at timestamptz not null default now(),
  primary key (user_id, kp_id),
  check (layer <> 'drop' or drop_reason is not null)
);
create index idx_path_order on user_path (user_id, layer, seq);
```

三处修正：

- **三层结构终于有家**：底线层 / 主攻层 / 放弃层（卖点"告诉你别学什么"）此前无字段承载，现在 `layer` 明确；`skipped`（用户自报跳过，进抽查池）与 `layer='drop'`（系统建议放弃）是两码事，不再混在 `practice_st` 里；
- **放弃理由可存**：`drop_reason` 是差异化卖点本身，必须有字段；
- **`auth_source` 从单值改可多值**：初版是 `text not null` 单个来源，但"简历 + JD 同时命中"很常见，单值会导致权重 `×1.5` 该按哪个算说不清。改 JSONB 数组后，权重规则可明确为"按最高来源权重"，不再有歧义。

> **为什么和练习态拆两张表（粒度相同但生命周期不同）**：路径骨架只在"建档 / 重新开方"时重建；练习态每次练习都在动。拆开是为了让"重建路径不丢练习进度"成为 DB 层保证（重开方只重写 `user_path`，`user_kp_state` 原地不动），这正是第三节"重置语义清晰"的落地。

### 4.13 作答记录

```sql
create table attempt (
  id          bigserial primary key,
  user_id     text not null references app_user(user_id),
  kind        text not null
              check (kind in ('合卷练','复测','模拟考','抽查','真实复盘')),   -- v2 补"真实复盘"
  started_at  timestamptz not null default now(),
  finished_at timestamptz,
  aborted     boolean not null default false
);

create table answer_log (
  id           bigserial primary key,
  attempt_id   bigint not null references attempt(id),
  user_id      text not null references app_user(user_id),
  kp_id        text not null references kp_main(id),   -- v2 补 FK
  layer_key    text not null,                          -- 层稳定键，对应 followups[].layer_key（v2）
  dir          text,                                   -- 冗余便于按方向聚合
  answer_text  text,                                   -- 允许空（答况="空"）
  is_blank     boolean not null default false,         -- v2：显式标记空答
  answer_src   text not null default 'text' check (answer_src in ('text','voice')),
  score_level  text check (score_level in ('excellent','good','pass','fail')),  -- 部分物化的档位（v2）
  verdict      jsonb not null,                         -- 判定明细（含 layer_key + level + 要点文本快照）
  verdict_model text,                                  -- 判定用的模型，审计与漂移分析
  appeal       text not null default 'none'
               check (appeal in ('none','requested','accepted','rejected')),    -- v2：申诉/纠正
  created_at   timestamptz not null default now()
);
create index idx_answer_kp      on answer_log (user_id, kp_id, created_at);
create index idx_answer_layer   on answer_log (user_id, kp_id, layer_key);
create index idx_answer_attempt on answer_log (attempt_id);
```

关键细节：

- **`verdict` 里存命中的要点快照，且快照带 `layer_key + level`**：评分要点将来会被校对改写，判定历史引用的是"当时的标尺"。不存快照，rubric 一改历史判定就不可解释；存了快照，rubric 改动只影响未来判定。**历史可解释性靠快照，不靠冻结库**；加了 `layer_key` 后，"断在第几层""深度分布"才随内容校准保持可比；
- **`score_level` 是部分物化**（v2）：档位、命中分布是跨场聚合的核心（"证据密度 0.1 → 0.4 → 0.7"、简历主张存活率），全藏在 JSONB 里没法索引聚合。把最常聚合的**档位**提成实列，明细仍在 `verdict`；
- **`layer_key` 索引**（v2）：支撑"这个考点卡在第几层"的跨场查询；
- **`is_blank` / `answer_text` 可空 / `appeal`**：见 2.13；
- **`verdict_model` 记录判定模型**：换了判定模型后效果波动，可以按模型分组回看判定质量。

### 4.15 JSONB 还是子表：统一判据与自查

判据只有一句：**按整体读写且无独立查询需求 → JSONB；需要跨实体按子结构查询、或有独立生命周期 → 子表。**

按这条判据自查（v2 修正了两处不达标）：

| 内容 | 存储 | 是否达标 |
|---|---|---|
| `variants` / `level_expect` / `detail` / `core_answer` | JSONB | ✅ 整体读写、无子结构查询 |
| `followups` / `rubric` | JSONB | ⚠️ 保留 JSONB，但**必须有稳定 `layer_key` + JSON Schema 校验**（覆盖度报告是"跨考点按 dir 聚合"，严格说已越过纯 JSONB 的边界；用 `answer_log.dir` 冗余列兜住聚合） |
| `answer_log` 的档位 | 实列 `score_level` | ✅ 从 JSONB 提列，满足跨场聚合 |
| 前置关系 / 频率信号 / 用户态 / 作答记录 / 方向状态 / 个人私有内容 | 子表 | ✅ 有独立查询模式或独立生命周期 |

**两个必须写进管道的要求**（初版完全没提）：

1. **JSONB + AI 生成 = 键名漂移风险**：所有 JSONB 的键名必须由**模板固定 + JSON Schema 校验**，否则 AI 成稿时键名/类型一漂移，消费方（前端、判定器）直接解析失败，且没有 DB 层兜底；
2. **"将来迁移不迟"要成立，前提是先有稳定键**：初版说"字段是稳定枚举、迁移可控"，但 `followups` 已被 `answer_log` 以"层"语义引用——没有 `layer_key` 就无法把历史映射到新结构。v2 补上 `layer_key` 后，这个前提才真正成立。

## 五、内容生产管道

题库质量的上限在管道，不在 schema。七个环节，每个环节写清 AI 干什么、人干什么：

```
采集素材 → 文档解析与拆题 → 聚类去重 → 考点成稿 → 人工校对 → 入库上线 → 持续演化
```

1. **采集素材**：面经、开源仓库（JavaGuide 这类）只取"哪些题被反复问、问到什么深度"——出现次数、来源岗位、有没有追问记录。素材以 pdf / doc / docx / md 形式上传（技术方案见 [系统架构设计](系统架构设计.md) 4.4），落 `kp_source_doc`；
2. **文档解析与拆题**（v3 新增）：上传文件先抽成纯文本（人先看解析预览，确认没抽错），再拆成单题写入 `kp_candidate`。拆题策略三档：按标题层级 / 按题号正则 / 交 LLM 切（兜底）。候选记录带 `doc_id` 溯源回原文件；
3. **聚类去重**（管道里最重要的一环）：把候选池的题面映射到已有考点——同一考点 n 种问法归一，归入 `variants`；映射不上的留候选池 pending。**去重是题库的生命线**：同一考点重复入库，练习时间被稀释、判定数据被分裂、前置图开始冗余。这一步 AI 做语义匹配 + 人确认边界 case，**入库时 `unique(cluster_id, slug)` 在 DB 层再兜一道**；
4. **考点成稿**：AI 按固定模板生成——题面、变体、叙述框架、追问链（每层带 `layer_key` / `dir` / `expect` / `stop_if`）、评分要点（带 `layer_key` + `level`）、从零讲（按簇）、职级差异。**模板是 schema 的填充器，成稿必须过 JSON Schema 校验**（防键名漂移，见 4.15）；
5. **人工校对**：校四样东西——技术正确性（参数、数字、因果链顺序）；**评分要点的可判定性**（不可判定的要点必须改写成可判定的，见 2.8）；变体是否覆盖面经主要问法；从零讲有没有讲错比喻。校过 → `reviewed` → `active`，同时写 `reviewed_at` / `review_due`。**簇级内容同校对、同状态流转**（v2）；
6. **入库上线**：状态机流转，同时把采集阶段的频次信号写入 `kp_freq_signal`（来源=面经）；
7. **持续演化**：复盘录题的真实信号回流 `user_kp_signal`（权重最高）；判定数据反过来暴露评分要点质量问题（某个要点在真实回答里从来判不出命中——要么写法不可判定，要么它不重要）；新真题进候选池。**题库不是建完的，是长出来的**，复盘信号是它的生长点。

> **"不抄正文"与"解析全文"不矛盾，但要划清界**（v3 补充）：解析出的素材文本是**AI 重写的输入**，不是入库的成品。合规红线守的是"最终内容不能是别人的原文"，所以：`parsed_text` 只作过程材料留在 `kp_source_doc`，**不进 `kp_main`**；成稿必须经 AI 重写 + 人工校对；入库时标注来源链接。上传私人收藏的面经自用没有问题，但**若将来要开放给他人使用，这一步必须重新审视**——这是版权上唯一的实质风险点 [Expert judgment]。

## 六、题型样板验证：商品详情设计（设计演进链）

schema 设计得对不对，纸上谈兵不算数——拿一条真实场景题把所有字段填一遍，哪里顺、哪里卡，设计自己会说话。选「商品详情页设计」：它是我简历上真实做过的系统（QPS 8k、缓存命中 97%），覆盖缓存、一致性、热点、限流四个技能域，是场景题里和画像重合度最高的一条。这条考点经历了两轮设计验证，6.2 记录了全过程。

### 6.2 验证结论：三轮验证，设计收敛

这条考点经历了三轮验证，每轮都改了设计——诚实记录全过程。

**第一轮（独立题型假设）**：五步脚手架 + 平行三板斧 + 维度计分。结论：七张表零改动，四处修正落在内容约定层。但留下三个别扭：场景题没有标准形态的从零讲、维度计分要单独一套换算、20 分钟整卷对新手门槛过高。

**第二轮（演进链，被"为什么不能做成知识点模式"击穿）**：把五步展开为演进链——第 1 层最简版，每层条件升级逼出高端方案。验证结果：

- **题型枚举 3 → 2**：演进链与追问链结构同构，`sub_type='design_chain'` 区分语义——字段结构零新增；
- **评分统一**：维度计分取消，按层要点命中走统一四档规则；从零讲回归标准形态（第 1 层"最简版为什么扛不住"）；
- **渐进式练习成立**：每层 5 分钟、从最简版起步——场景题第一次变得新手友好；
- **耐力训练不丢**：合卷练全链连讲 20 分钟 + 模拟考乱序抽层（防背题）。

**第三轮（分级制 + 方向覆盖，被两个追问击穿）**：「场景题也能有标准完美答案」+「追问选了一个方向，另外两个会丢吗」。验证结果：

- 簇级挂 `reference_solution`，评分从"命中标准答案"变"**在完美答案的坐标系里定位深度**"；
- 评分要点分级制（基础 / 中级 / 资深）：资深级想到加分、不想到不扣；
- followups 加方向分组（`dir`）+ `user_dir_state` 承载覆盖保证——**方向不会丢，只会延后**。

**v2 修正（第四轮，被架构评审击穿）**：三轮都在概念层收敛，但物理层留下了硬伤——层没有稳定键、`sub_type` 没落表、个人信号混进库表、DDL 建不出来。修正：给层加 `layer_key`、给题型加 `sub_type` 列、把个人信号拆进 `user_kp_signal`、修 DDL 并补全约束与缺失实体。**元结论**：概念边界（§二）三轮几乎零返工，是最值钱的部分；真正要返工的全在"承重实体的身份"与"物理层的可执行性"。

## 七、场景兼容性检查

设计完不是自嗨，拿真实面试场景逐个过一遍，每个场景都要有明确的承接机制：

| 真实面试场景 | 考点库的承接 |
|---|---|
| "你简历写的 X，讲讲" | 项目叙事题型 + `user_path.auth_source=简历` |
| "为什么不用 X 而用 Y？" | 追问链里的对比层（`dir=取舍`）+ 评分要点加分项 |
| "线上出过什么事故？" | `user_case` 个人案例（建档/复盘入口产生，属用户态） |
| "你只说了一半，再想想" | 同层变体追问（答况=缺/错时的既定动作，AI 在 rubric 内改写） |
| "你没实际用过吧？"（试探虚报） | 抽查池机制：自报跳过的考点低频抽验，虚报反复出现 |
| 被问到库里没有的题 | 复盘录题 → `kp_candidate`（来源=真实面试）→ 题库生长点 |
| 跨域题（Redis 缓存 + ES 一致性） | 只挂主簇（有损）+ 前置跨域引用——不复制考点，用依赖表达 |
| 同一技术不同深度（HashMap / ConcurrentHashMap） | 各自独立考点 + 前置关系（能单独成题的不合并） |
| 面试官层层下钻到答不出 | 追问层 `stop_if` + 职级停止点，`answer_log.layer_key` 记录"断在第几层" |
| 反问环节 / HR 面 / 行为面 | 显式范围外（见下），不假装能承接 |

**检查结论**：八类问法全部有承接机制。v2 补齐了两处原先的挂载空洞——"个人案例的采集与挂载"落 `user_case` + `user_narrative`，"断在第几层"落 `answer_log.layer_key`——初版把这处结构性缺口记为"待细化"，现在有了明确落点。

## 八、明确的范围外

- **算法手撕**：显式进放弃层（`layer='drop'` + `drop_reason`），写明原因和替代方案（LeetCode），不让它沉默缺席；
- **行为面 / HR 面**：v2 议题，现在不进 schema——八类问法里没有它，schema 也不用为它预留；
- **多语言考点**：先 Java 后端一个域跑通，`skill_domain` 字典天然支持扩展，不用提前设计。

范围外的意义：schema 里没有它们的字段，将来加回来也不需要改表——题型是枚举 + JSONB 扩展，这正是当初选 JSONB 的原因之一。

## 九、落地顺序

1. **建表**：`skill_domain` / `kp_cluster` / `kp_main` / `kp_prereq` / `kp_freq_signal` / `kp_source_doc` / `kp_candidate` / `app_user` / `user_plan` / `user_skill` / `user_path` / `user_kp_state` / `user_kp_private` / `user_case` / `user_narrative` / `user_dir_state` / `attempt` / `answer_log` / `user_kp_signal` 共 19 张表 + 查环校验（事务内）+ 全量 CHECK 约束。**先跑通 DDL 语法**（初版就有建不出来的索引）；
2. **先标 10 个考点走通全流程**（不是 50 个）：**8 个 `default`**（ES 写入链路簇做样板——每条手工标 `difficulty`、评分要点带 `layer_key`+`level`、三档标准样例、2 个变体、追问链带 `stop_if`）+ **1 条 `narrative`**（商品详情系统叙事，验证六要素模板 + `user_narrative` 事实确认）+ **1 条 `design_chain`**（第六节样板，验证按层判分）。全部走完 `draft → reviewed → active`，同时验证判定 prompt；
3. **样板验收标准**：一条考点能同时喂饱路径排序（难度 + 前置 + `user_path.layer`）、学习卡片（框架 + 从零讲 + 职级目标刻度）、模拟考判定（rubric + 变体 + `stop_if` + `layer_key`）三个消费方，不用任何字段改写。三类 `sub_type` 各验一条；
4. **批量录入素材**：把手上收集的 pdf / doc / docx / md 批量上传解析、拆题入候选池（先跑 `dryRun` 看拆题效果），再走管道到 50 个考点——AI 成稿 + 校对 + **JSON Schema 校验**，去重规则从第 2 步样本里沉淀成 checklist；
5. **复盘信号回流**在第一次真面试之后接入——`user_kp_signal` 是管道闭环的收口。

一句话收束：**库里存的是结构化的"怎么问、怎么判"，态表存的是"这个用户到哪了"，管道保证内容可信，信号让它越长越准。**schema 是简单的，难的是概念边界（追问层不是考点、簇不是依赖、难度不是职级）——边界守住了，后面的判定、路径、报告才有干净的数据可用。
