## 二、C 端模块

### 2.1 建档

用户进入产品的第一站，也是简历档案的管理入口。每个用户最多维护 3 份简历档案，档案是备考上下文的顶层归属：一份档案包含简历原件与解析文本、技能画像、备考计划、项目素材，生成关卡、闯关、抽卡、模拟考、复盘的个人态全部挂在档案下，切换档案即切换备考上下文，进度互不污染。建档动作发生在档案内：有简历就上传解析，没有简历就跟 AI 聊——年限、岗位、做什么、用过什么。AI 从简历和对话里两阶段生成技能条（先起草条目、再逐条锚定知识点），用户逐条拍板：不熟的删掉、漏掉的加上、措辞不准的改掉。对话里聊到的项目细节（数字、冲突、结果）作为项目素材沉淀下来，后续成为项目叙事和模拟考追问的原料。

含义与边界：

- 产出四样东西：定稿的技能条集（user_skill + user_skill_kp，LLM 两阶段生成 + 用户逐条确认，锚定集即授权数据源）、目标职级（user_profile.level_target，CHECK 约束五档：初级/中级/高级/资深/专家）、备考计划（目标岗位/JD/周期/每日时间，user_plan）、项目素材（user_case），全部归属当前简历档案。目标职级是全链路的深度标尺：过关停止点、基础关卡组组成、模拟考下钻深度都由它推导；建档时用户明确说了就采用，没说就按工作年限推测缺省值，用户随时可改——32 岁面中级岗，全套按中级复习，完全合法。（年限→职级缺省映射表待定义，见暂缓功能清单。）
- 技能条是个人侧的简历能力段落（一段简历措辞 + 一组锚定知识点）：授权锚点从簇下沉到知识点，主攻层"简历上写了的"由锚定集定义，简历主张存活率也以它为锚；跨条重复锚定合法，0 锚定条（软素质条）打标记、不进存活率定义域；简历的项目部分不在技能条承载——项目素材在建档采集，六要素模板在知识库（见 2.3 叙事题型）。
- 无简历用户同样建档：对话收集年限、岗位、技术栈，档案形态为不含简历原件的默认档案，其余流程与有简历用户完全相同。
- 画像走状态机（草稿 → 确认 → 定稿，落 user_profile.skill_status），存在未确认条目时不得定稿，未定稿的画像不参与生成关卡。
- LLM 在这里只做选择与组织（对齐预制知识菜单，幻觉考点 ID 被结构校验拒绝）；技能条中的事实数字按不过分干预口径处理；建档不答题、不摸底，入口永远没有考试。
- 简历主张的降级/升级建议写回触发它的那份档案，档案间互不串写。
- 不碰知识点内容，不碰练习进度。

落点：后端 profile 包，拥有简历档案实体与技能条（user_skill / user_skill_kp）；依赖知识库（域/簇/考点菜单）、文档解析（简历抽文本）与模型接入（技能条起草，LlmPurpose.profile_draft）；生成关卡、模拟考、复盘经 profile api 消费定稿技能条。

### 2.2 生成关卡

基于档案内定稿画像与备考计划，把知识库裁成属于这份简历的一组组可打关卡。检索与组织分开：检索用技能条、项目素材、目标 JD 和**目标职级**去匹配知识点，决定哪些内容进关卡、权重多高；组织不按技能条（个人态，增删改名会抖动骨架），按知识库现成的「技能域 → 主题簇 → 知识点」结构展开为**关卡制**——每个技能域一个关卡组，组内按主题簇分关卡、关卡内按难度与前置拓扑排序；职级基线做成第一个「基础关卡组」（不分域的目标职级必问基础，靠前快速过）。先闯哪组用户自选（系统给默认序：基础关组 → JD 相关 → 库级频率信号 → 授权密度），全部关卡组完成 = 这份简历的知识库学完。跨域前置在学习地图上表现为锁：前置所在关卡组未完成到相应关卡，本组关卡上锁，防止跳跃式推进。

来源与权重不落库，全部消费时推导（聚合权重按字段推导，不单独存库）：某知识点是否简历授权，由它是否被当前档案定稿技能条锚定推出（查 user_skill_kp），承载模拟考聚合权重 ×1.5 与简历主张存活率的定义域；是否职级必问（进基础关组），由目标职级的基线规则推出，承载权重 ×0.8；是否信号回流，由 user_kp_signal 反查得出。关卡数据只存关卡组与关卡的序列本身（顺序、前置锁），不存任何来源标记；放弃决策、过关状态等个人态统一写 user_kp_state（见 2.3），重开时按 user_kp_state 的放弃标记过滤关卡。

不进关卡的内容分两种。一种是未命中：画像授权、职级基线、JD 与个人信号都不指向的内容，天然不进，不展示也不留痕。另一种是显式放弃：用户在学习地图或闯关途中对关卡里的题手动点击放弃，它移出关卡组、进入放弃分区，原因可选填。放弃清单 v1 只由用户手动维护，系统不做自动标定（职级×时间预算的自动减法、算法手撕的预置放弃都不做，留到以后）；算法手撕在知识库范围外，学习地图上以一行静态说明提示替代方案（LeetCode），不做成数据。重新生成关卡保留用户的放弃决策，不重新计算。

含义与边界：

- 域与难度之争的取舍：关卡制让"域放在一起"（组内）与"难度递进"（关卡内）同时成立，牺牲的只是跨域全局难度递进——跨域难度本不可比，这个牺牲是干净的；跨域依赖用锁表达。
- 难度不是准入门槛，只是排序属性：进关的题集由四信号（画像授权、职级基线、JD、复盘信号）并集决定，任一命中即进，与难度无关；难度只决定关卡内的排序与卡面颜色。禁止任何"按用户职级过滤难度带"的逻辑（如高级只抽橙红卡）——那会结构性漏题：同一道题对不同目标职级的用户是同一道，差的只是过关深度（见 2.3 停止点）。
- 技能条删除或修改的语义是修正真实水平，不是决定不学：职级基线与 JD 信号不随删除消失（HashMap 对面中级岗的人必问，删了反而更需要练）；"不学"只发生在放弃分区的显式决策里。
- 核心动作是"裁"：每个知识点的具体内容不现场编，从预制知识库按需取用，点开才渲染；学习地图是独立页面，C 端日常主入口。
- 可重开：复盘信号回流、简历主张降级之后重新生成关卡；重生成只重写关卡组与关卡（user_path），练习进度（user_kp_state）原地不动，闯关游标按新序列与掌握状态重新定位。

落点：后端 learning 包（与闯关、抽卡同包，开发任务独立），产出挂在简历档案下；依赖知识库（读知识点、难度、前置、域与簇）、建档（读定稿画像）、复盘（消费个人信号，走数据回流，见第五节）。

### 2.3 闯关

日常主体。学习地图上选一个关卡组进入闯关页，任务是完成这个关卡组：从当前关卡继续往前，组末即该域完成。闯关不设"每日抽卡"，去哪个组、闯几关完全由用户自控，没有随机调度。

每个关卡就是一张闪卡题组：初始只展示题目，用户先回忆，再翻面看标准答案；有更深一层的关联题目（追问）就展示入口；看不懂展开知识簇看从零详解；还不懂，后续版本针对这道题与 AI 对话交流。过关方式两种节奏并存、用户自选：闪卡快过——翻面自评「过了」直接往前（想快速过一轮拿印象的人）；练习模式扎实过——闭卷打字作答（语音转写二期接入），先作答才解锁自评，作答经判定引擎驱动下一步（继续下钻、同层换角度再问、回退前置知识点），答过才算判定过关。卡面上「我不会」与「我会，跳过」合并为过关选择：标了"不会"的卡进抽卡的弱点加权与复测队列；不想要的题可点击放弃，移出关卡组进放弃清单。

含义与边界：

- **快过与练习的双轨口径（已拍板）**：闪卡快过算过关推进，但在 user_kp_state 上单独落"快过态"标记（区别于"练习判定过关"）；快过态的卡同样进入抽卡验伪范围——抽查池对快过态卡上调抽中概率，与"我会，跳过"的抽查同等对待，虚报同样打回复测队列。即：快过是显式的低保障通道，挤水机制延伸覆盖它。关卡过关按"快过或练习任一过关"计，但报告与存活率只统计练习判定的数据。
- 闯关纯推进、组内不回头：复测与复习全部交给抽卡模块，闯关只负责向前——两个功能互不打扰，节奏各自干净。判定动作里的"回退前置知识点"是内容层回退（就地展开前置知识点的资料讲解/闪卡），不改变闯关游标。
- 练习模式不设场次实体：逐关作答逐关判定，attempt 仅模拟考使用（练习作答的判定历史 attempt_id 为空）。练习模式未过关（答况为错/空且变体再问仍不过）的关卡留在当前关，引导先看前置知识点或资料讲解，下次进组从该关继续；用户可随时切闪卡快过。
- 同一道题，不同目标职级过关深度不同：过关标准由知识点的职级要求（下钻停止点）决定——面中级答到第 1 层算过关，面资深要扛到第 3 层；停止点之下的更深追问层照样可见（学无止境），但目标刻度明确标注"到你目标职级讲到第 N 层算够"。同一关卡组对不同用户是不同题集（四信号裁剪）+ 相同题目、不同尺子（停止点）。
- 漏题的三道防线：并集准入（不做难度/职级过滤）；复盘兜底（真被问到的题不在组里，录题回流下次生成进组）；标定进校对清单（职级基线与停止点的完整性是内容管道人工校对的必检项，见 3.6）。
- 关卡即题组，重玩成本低：单关 3 分钟量级，随时进来随时闯，进度就是"闯到第几关"，不需要每日任务感。
- 过关选择里"不会"是抽卡的输入信号（弱点加权 + 复测队列），"我会，跳过"进抽查池由抽卡验伪——自报水分的挤压器在抽卡侧。
- 卡面按知识点难度配五色：难度约定为 1~5 整数档，与白/绿/黄/橙/红五色一一对应（1 最易、5 最难）。闯关、学习地图、抽卡共用同一套难度配色；颜色只编码难度，简历授权等来源信息用角标区分，不抢颜色语义。
- 题卡内容映射，闯关、抽卡、模拟考三处共用同一套卡结构：正面 = 题面（练习与模拟考中按问法变体或现场改问法呈现）；背面 = 标准回答样例，默认展开及格档，良好/优秀两档可展开；追问入口 = 追问链，按 layer_key 逐层展开；看不懂 = 展开挂载的资料讲解（kp_doc 按 kp_doc_rel 排序取 active 资料列表，资料讲解需求侧三级流程）；目标刻度 = 该知识点职级要求按当前目标职级渲染出的停止点（「讲到第 N 层算够」）。评分要点只进判定引擎，不上卡面。
- 关卡与过关口径：关卡 = 主题簇，关卡过关 = 关卡内全部知识点过关，到组末即全组完成；过关选择（过了 / 不会 / 我会，跳过 / 放弃）与练习模式判定结果统一写 user_kp_state——它是闯关游标、抽卡卡池与三条抽卡信号的共同数据源，抽卡卡池即 user_kp_state 中已过关知识点的集合。放弃决策同样落 user_kp_state 标记位（见 2.2），重新生成时，放弃的知识点不进组、进放弃分区。
- 项目叙事的练习（看标准故事 → 练习模式作答，讲 3 分钟的口述形态随语音转写二期接入）归这里；标准故事由档案内建档素材起草，六要素组织，每个数字和事实逐条经用户确认。叙事卡的库侧承载是 sub_type=narrative 的模板知识点（题面模板 + 指标清单评分要点，不含任何个人内容），个人标准故事挂 user_narrative 并关联模板知识点与档案，多项目按 project_name 区分——库/态分离在叙事题型上的落地。

落点：后端 learning 包，状态挂在简历档案下；依赖判定引擎（仅练习模式与模拟考消费）、知识库、生成关卡（关卡序列与练习态分表，重新生成不动练习进度）。

### 2.4 抽卡

随机学习与随机检验的轻量入口，全部复习机制在这里，也是**每日回访的默认锚点**（不建每日卡与任务系统，"今晚先抽一把"就是打开产品的理由，支持全随机或指定域连抽——单抽/3 连，配简单翻牌动画，适合碎片时间）。卡池 = 已闯过关卡里的卡（闯关走过的部分），按三条信号混抽：SM-2 到期的复测卡（间隔重复的主引擎）、抽查池到期的验伪卡（闯关时标「我会，跳过」以及快过态的卡，低频弹出翻面复验，虚报打回复测队列并累积虚报证据）、闯关时标「我不会」的弱点卡（抽中权重上调）。抽卡既是复习器也是自报水分的挤压器，闯关因此可以放心纯推进。

抽卡体验轻：翻面自评为主，橙红高难卡可选进入判定（想要真检验时用，复用闯关练习模式的判定流程）；趣味性保留翻牌动画与连抽，不引入积分、连击等游戏数值系统，不设正式报告。

混抽权重按会话状态动态调整，第一版就要有：连对降权与低难度穿插卡。连续答对的卡在随机混抽中下调抽中概率（只调概率，不碰 SM-2 到期队列与抽查池的入场资格，权重设下限不为零——"变没"交给间隔重复去做）；连续答错达到阈值时，后续抽卡掺入少量已过关的低难度卡（难度 ≤ 2，对应白绿卡面），重建正反馈与掌控感。两者互补关系：SM-2 管"错的卡间隔重置后回来"，低难度穿插卡管"连错时当场给正反馈"；穿插卡作答结果照常写 SM-2 参数，就是一次正常复习，不产生额外状态。连对/连错计数落 user_kp_state 实列标记位（内部状态，不做 UI 展示），不加表。

含义与边界：

- 三条抽卡信号（到期复测、抽查验伪、弱点加权）都由闯关的过关选择喂养，抽卡不自己产生新任务：闪卡自评、练习判定、抽查复验都更新 user_kp_state 的 SM-2 复习参数与标记位（弱点标记、抽查池状态、虚报证据计数、快过态标记），字段随详设定稿。SQLite 纪律（CLAUDE.md 陷阱 E）：SM-2 的下次到期时间 due_at 必须实列化并建索引 `(profile_id, due_at)`——抽卡按 due_at 过滤是日常高频查询，不能埋进 JSON；easiness/interval/reps 等非查询参数可存 JSON；连对/连错计数、虚报证据计数同为实列标记位。
- 指定域抽卡天然支持考前抱佛脚：明天面 ES，今晚连抽 ES 组。
- 抽卡数据（复测通过、虚报证据）回流影响两个下游：弱点卡决定抽中权重，简历授权卡的虚报/失败累积汇入复盘的降级建议。

落点：后端 learning 包，与闯关共享练习态；依赖知识库、生成关卡（界定可抽卡池）。

### 2.5 模拟考

复习好了来一套的全真检验：**全套真实模拟考**（不分级入场——按域检验的职能由抽卡承担，指定域抽卡 + 橙红卡进判定就是按域的即时检验），**每天一次机会**（attempt 按天限一次，防高频刷考烧判定成本），有时间限制、有评分、出题规则贴近真实面试。入场不设通关解锁——组卷范围由四信号（画像授权、职级基线、JD、复盘信号）与库级频率信号推导，不依赖闯关进度，"考前一周没资格考"的结构性冲突不存在。方向轮转组卷（先横切再纵深），每答一问判一次、判定驱动追问（对则下钻、缺则继续钻、错则温和纠正后同层换角度、空则切题），考完出三样东西：加权及格率（映射四档总评：优秀/良好/及格/不及格）、简历主张存活率、教练总评（LLM 只写叙述与归因，不给分）。

含义与边界：

- 简历主张存活率 = 本场抽到的简历授权知识点里没被打穿的比例（授权由技能条锚定推导）；连续两场低于 50% 自动触发简历降级建议——"简历和知识库互相改"的量化落点。降级建议与存活率机制一期保留，对用户可见；呈现细节（建档说明页、教练措辞、一键驳回）二期打磨（登记见[暂缓功能清单](暂缓功能清单.md)），写回触发它的档案走 profile 模块 api。
- 判定的同步/异步：练习模式同步判定（等判定回来驱动追问）；模拟考作答流与判定流并行——判定回来才出追问，等待期 UI 明示"面试官在记录"，考试计时只计作答时长，判定超时（15s）不扣作答时间；最终评分（加权及格率/存活率/教练总评）异步生成。超时与非法 JSON 同走"重试一次→降级自评"。
- 判定可申诉（v1 做"标记申诉"折中方案）：口误、用词不准等可纠正判定，结果页固定"我有异议"入口，点开可见该次判定引用的用户原话，一句话提交标记。标记后该判定进人工复核队列（**申诉复核队列随二期实现，登记见[暂缓功能清单](暂缓功能清单.md)**——队列就位前申诉标记照常落库，由人工处理改判），复核确认后手动改判为"不计入档位"——v1 不做 AI 自动改判，救济通道从第一天存在，改判权留在人手里。
- 中途喊停的场次照常出报告，标"未完成不评级"；连着两场喊停，考前说明里给提醒。
- 设计演进链以演进链形态进模拟考，平行方向乱序抽层防背题；未覆盖方向进下次优先队列，覆盖度进报告。
- 跨场趋势（断在第几层、扛了几层、深度分布演变）比单场评级值钱。

落点：后端 exam 包；依赖判定引擎、知识库、profile（写降级建议，走 api）。组卷不依赖闯关进度，learning 依赖随之取消（模拟考与 learning 无编译依赖）。

### 2.6 复盘

真去面了，回来把被问到的题录进去。能对上已有知识点的，写成个人复盘信号（权重最高的频率信号），作为最高权重输入供关卡重排消费；对不上的，进知识库候选池，成为知识库的生长点。同时触发它的那份档案里，路径和简历跟着更新：练不住的主张从简历降级，练深了的知识点反过来写成简历亮点。

含义与边界：

- 体量小、杠杆大：五环节里唯一由真实面试驱动的环节，也是"知识库不是建完的，是长出来的"这句话的入口。
- 个人复盘信号与库级频率信号分开存放：前者是隐私资产、随面试次数累积；后者是公共信号，只含面经信号与人工标定。
- 录题匹配知识点的前提是 C 端能搜到知识点：需要按题面模糊检索 active 知识点的搜索接口（接口清单随各后端模块落地时定义，口径见第六节对照表）；匹配由用户确认，不做 AI 静默归并——归并错了会污染权重最高的个人信号。
- 与模拟考同属 exam 包，但作为独立开发任务，因为它横跨"录题回流"与"简历升降级"两条链路。

落点：后端 exam 包；依赖知识库（知识点匹配与候选池）、learning（写 user_kp_signal，走 learning api）、profile（写升降级建议，走 api）。**user_kp_signal 表归 learning 包拥有**：复盘经 learning api 写入信号，生成关卡在重排时直接读本模块表——依赖方向 exam→learning 单向，依赖图无环。

### 2.7 账号认证

定位调整后的新模块：产品首版即以小规模公开服务运行（腾讯云部署，经 CSDN / 小红书引流），注册登录从"将来再说"变成硬前置——陌生用户上传的是真实简历，数据隔离与口令保护缺一不可。账号结构为**完全双表双入口**：客户（sys_customer）与后台人员（sys_staff）分表、分登录入口、两套会话互不通用。

- **注册**：用户名 + 口令 + 图形验证码，开放注册，写 sys_customer——低门槛承接引流转化，不做邀请码（与发帖引流的目的冲突）；不接短信 / 邮箱验证（"v1 不引外部服务"的既定原则），脚本防御靠验证码、注册与登录接口限流、单用户 LLM 硬熔断三道闸。注册成功即创建默认简历档案（2.1 的无简历档案形态），直接进建档。
- **登录与会话**：口令散列存储；C 端登录入口与后台登录入口完全分开，两套会话互不通用——客户 token 进不了 /admin 接口，员工 token 进不了 C 端 /api 接口；会话方案（JWT 或服务端 token）随实现定，PRD 不锁。未登录可达页仅五个：C 端登录 / 注册、后台登录、知识卡分享公开页 `/share/:kpId`、404。
- **数据归属**：档案归属客户账号（sys_customer），账号 1 : 档案 ≤3；历史单机数据迁移 = 你的练习档案归入你自己注册的客户账号。
- **内部协作账号**：几位同事以内容维护者（editor）身份参与题库生产，员工账号由管理员在后台创建（走 sys_staff，不经公开路径，初始口令线下交付；后台登录入口不做公开引流）。双表分立意味着员工账号与客户账号互不相通：同事要试用 C 端，另行注册客户账号。
- **v1 边界**：无找回密码（员工与客户两侧都走管理员后台重置）、无第三方登录、无邮箱验证、无注销账号（停用即可）；记住我、修改口令随后续版本。
- **成本与滥用防线**：LLM 限额对每个客户账号生效（成本控制只落在单用户维度，B 端生产类不设限额，见 4.2）；概览页提供用量视图与异常监控。

落点：后端 account 包，拥有 sys_staff / sys_customer 两表；被 profile 依赖（档案归属客户账号）；C 端登录 / 注册、后台登录、知识卡分享为仅有的公开接口；/api 接口只认客户会话，/admin 接口只认员工会话（web 层横切，两棵接口树各自校验、互不认对方 token）。

## 三、B 端模块

> B 端已随 T0-T9D 全部落地。本节按**功能模块**拆分：一个前端完整功能页 = 一个模块，无前端界面的纯后端重要逻辑单列（如血缘自动挂载）。内容生产主流程：素材库（原始资料加工）→ 候选池（研判）→ 知识地图（归一与成稿）→ 知识点管理（本体维护）→ 资料讲解（挂载）→ 校对流转（发布门），每模块小节讲职责与边界；操作级全流程（状态机、接口清单、按钮对应、端到端走查、现存缺口）见 [B端知识库与面试题维护全流程](B端知识库与面试题维护全流程.md)，本节不重复操作细节。字段级 DDL 以 `schema.sql` 为准。
>
> 内容侧公共约定（跨模块红线，各模块不再重复）：①**库/态分离**——全局内容进 kp_*，个人数据进 user_*，用户独一无二的内容绝不进全局库表；②**不校不上线**——内容状态机 draft → reviewed → active（下线/合并转 retired），未过人工校对不许进用户路径，库校对只重写内容、不碰用户进度；③**命名口径**——原子单元是知识点，主题簇、前置依赖、追问层、评分要点全部围绕知识点组织，"题库"一词只留给竞品语境；④**版权红线**——素材原文入池即焚，绝不进内容表，成品必经重写加人工校对并保留参考出处。

### 3.1 素材库（/admin/docs）

原始资料的加载与处理入口，内容管道的进料段（T6/T6R 已实现）。来源：面经、GitHub 仓库、CSDN 帖子、官方手册、书籍等；进料统一为页面上的新增 / 上传 / 编辑三类入口，来源出处必填（链接或书名 / 手册章节）。每个素材是一篇文档（kp_source_doc），经两道人工门加工为标准稿后拆解入池。

含义与边界：

- **六态状态机**：pending → approved → preprocessed → pooled；rejected / preprocess_failed 为异常分支，reopen（退回待审核）仅 preprocessed 可走——pooled 拒绝（原文已焚）。
- **两道人工门**：门1 人工审核（approve / reject，驳回需原因）——挡"不该进管道的资料"，是进入机器加工的唯一通道；门2 复核入池——LLM 重写产物经人工确认要点清单与拆分调整后才入池，挡"整理过程引入的错误"。
- **LLM 预处理重写**：审核通过后一次调用完成清洗、定类（article 文章 / question 面试题二值）与格式标准化，产出标准稿 std_text（含二级标题锚点，即入池拆分依据）；图片引用原样保留。preprocessed 可重跑（先清名下 pending 候选再覆盖），名下候选已被归一吸收的拒绝重跑。
- **入池即焚**：复核入池按锚点确定性拆分（不调 LLM）逐条建候选，同一事务内 raw_text 置空——此后系统只保留标准稿；pooled 态拒绝重跑与退回，唯一修改入口是编辑标准稿后重新入池，想改原文只能重传。
- **编辑失效语义**：approved / preprocess_failed 保存正文后回退 pending（审核失效）；rejected 保存即重新提交；preprocessed / pooled 不可编辑原文。
- **反推出题**：pooled + article 型可对勾选的锚点单元用 LLM 反推面试问法，产出 question 型候选（单元清单与当前标准稿不一致拒绝）。
- **图片资产「落盘即真相」**：无资产表——落盘路径按约定编码 data/source-assets/{docId}/{引用路径}，渲染走 `/api/admin/docs/{id}/source/**`（员工会话），删除文档连带删整个图片目录。
- **删除守护**：名下有任何非 pending 候选拒删（在途）、有候选被归一吸收拒删（防覆盖源孤儿化）；通过后连带删候选与图片目录，kp_doc 快照不受影响。

落点：后端 pipeline 包，拥有 kp_source_doc 表（入池产出的 kp_candidate 归候选池模块）；接口 `/api/admin/docs`；LLM 用途 doc_rewrite / question_gen。

### 3.2 候选池（/admin/candidates）

入池候选的人机协同研判（T6/T8 已实现）。候选 = 从素材拆出的最小答题单元或反推问法（kp_candidate，溯源回素材文档），状态机：pending（待研判，唯一可操作态）→ merged（并入已有知识点）/ discarded（放弃）终态；converting → converted 由成稿引擎驱动；matched 为预留态（当前无写入路径）。

含义与边界：

- **AI 匹配建议**：embedding 相似度输出 merge（并入哪个 kp）/ new（建新题）与同题 peers，只给建议不改状态。
- **并入已有知识点**：逐条 appendVariant（幂等去重）→ 候选置 merged → 事务外血缘挂载源文档（见 3.5）。
- **研判新建**：建 confirmed canonical（judge_basis=manual）+ 归簇；成员保持 pending 仅挂 canonical_id——归一题才是研判身份，候选仍是待成稿语料；可勾「立即成稿」接着触发成稿。
- **删除守护**：已被归一吸收拒删；converting / matched 在途拒删。

落点：后端 pipeline 包，拥有 kp_candidate 表（研判新建写 kp_canonical；并入经 kb api 写 kp_main 变体并触发血缘挂载）；接口 `/api/admin/candidates`；LLM 用途 embedding。

### 3.3 知识地图（/admin/knowledge-map）

同题归一、语料组织与按簇成稿的操作台（T7/T8 已实现）。归一漏斗：结构归一 → embedding 精确 → LLM 对齐，同题候选聚合为归一题（canonical）；映射不上的进语料簇——确认后成正式簇（簇是知识点入库的前置）；地图产出域 → 簇 → 归一题三层视图与覆盖率，决定按簇建设顺序。

含义与边界：

- **归一题三态**：pending（AI 聚合待确认）→ confirmed（人工确认入图）→ built（已建设）。回退全路径：unbuild（误建设回退）、split（拆回重新研判，整题解散物理删 canonical 行）；built 拒拆（先 unbuild）。未拆散的 pending / confirmed canonical 行是回退与重试的操作对象，不是中间态残留。
- **按簇成稿**：LLM 从归一题的 N 份源答案生成知识点全结构（题面 / 变体收敛 / 叙述框架 / 追问链收割源递进设计 / 分级评分要点 / 三档样例 / 职级差异），layerKey 与 pointId 由后端确定性分配；结构校验（KpStructureValidator + MarkdownGuard：Mermaid 围栏 / 括号配平）失败带错误反馈自动重试一次，再失败落 failed 记录、可重试。
- **多源冲突不阻断**：源间矛盾随 success 记录内嵌落库，事后在地图页逐条人工裁决（resolved 写回）。
- **成稿成功链**：经 kb api 建 kp_main（draft）→ canonical 置 built + built_kp_id → 成员候选 converting → converted → 血缘自动挂载源文档（见 3.5）。成稿不等于上线，产物进校对流转队列。
- 成稿预估按 confirmed 归一题计，预计调用数与近 7 天 B 端用量在成稿前可见。

落点：后端 pipeline 包，拥有 kp_canonical / kp_compose 表（语料簇写 kp_cluster 的 draft 态；成稿经 kb api 写 kp_main）；接口 `/api/admin/knowledge-map`；LLM 用途 cluster_dedup / ai_compose / embedding。

### 3.4 知识点管理（/admin/kp）

知识库本体（知识点与簇）的维护页（T4/T9 已实现）。知识点 = 面试题本体：题面、问法变体、叙述框架、追问链（层身份+方向）、分级评分要点、三档样例、职级要求与下钻停止点、难度、前置、主主题簇、考频信号。簇管理弹窗（建簇/改簇/合并/状态推进）挂同一页。

含义与边界：

- **技能域**是全局一份的种子字典，唯一职责是知识点分域归属（簇挂域、筛选与关卡组按域组织），数据由种子维护、**无管理接口**（域数量级极小，界面化管理登记在暂缓功能清单），域下拉消费 kb meta 只读接口。域判据：域按**稳定的技术领域**切，不按具体技术产品切——数量保持在 6~10 个、极稳定，随内容生长只加簇不加域；ES、Redis、MySQL、K8s 这类具体技术落簇层、不立域，否则域清单随技术爆炸，建档清单与授权锚点跟着失稳。「Java 后端」这类语言主场景域是产品画像的主桶可以立，判据的实质是顶层桶要少而稳、具体技术不得与顶层桶平级。现有种子域 Elasticsearch 属历史样例，按此判据待归并（待决事项见开发计划一C）。
- 技能条（个人侧简历能力段落，user_skill / user_skill_kp）不归本模块，见 2.1 建档——本模块只向它提供域/簇/考点菜单。
- 题型收敛为一类知识点（type 单值），差异下沉到 sub_type 枚举：default / design_chain / narrative（枚举契约见附录 A）；全局骨架（如项目叙事的六要素模板）也放这里，全局一份。
- 上线后有复核到期机制（review_due_at），过期内容回人工复核队列；扫描与队列的自动化随二期，当前靠列表筛选人工巡检（登记见暂缓功能清单）。
- 概念边界最值钱也最容易守错：追问层是知识点的内嵌结构（layer_key 永不复用），主题簇是生产单位，前置依赖是学习维度，难度与职级要求互不推导，三者两两正交。
- 字段约定：难度为 1~5 整数档（对应卡面五色）；每个追问层必须标所属方向 dir，主问题层方向固定为 main，方向是模拟考横向轮转与覆盖统计的分组键；追问链编辑只许改文本与顺序，层的增减走「新增层 / 停用层」，停用层的 layer_key 不得再分配给新层——这是红线 2 的操作化。
- 内容格式：讲解类字段（叙述框架、三档样例、资料讲解 content_md）为 Markdown 白名单（代码高亮 / 表格 / Mermaid），判定链路字段（题面、追问层、评分要点）保持纯文本。
- 簇先于知识点存在（kp_main 挂且只挂一个主簇，外键决定建簇在前）：建簇入口两处——知识地图聚类环节按素材聚簇加人工确认、本页手工建簇/改簇/合并簇；簇是纯组织节点不承载内容，簇状态机只管组织态（可用/停用/合并），内容状态机在知识点与 kp_doc 各自落。
- 下线 retire 两模式：discard 弃用（清 merged_into）/ merge 合并下线（变体去重并入目标、记 merged_into）；retired 之后全链路封死——不能作合并目标、不能作前置依赖、不能挂资料、不能并入变体。
- 考频信号三来源：manual 人工标定 / interview 面经 / coverage 题库覆盖（成稿时由覆盖源数转入）。

落点：后端 kb 包，拥有 skill_domain / kp_cluster / kp_main / kp_prereq / kp_freq_signal 表（附录 A）；接口 `/api/admin/kp`（知识点）与 `/api/admin/clusters`（簇）；对内暴露 KbKpApi / KbClusterApi 供 pipeline 成稿与并入调用；被生成关卡、闯关、抽卡、模拟考、判定引擎依赖（C 端随 T10+ 开工）。

### 3.5 资料讲解（/admin/kp-doc）

资料讲解资产（kp_doc）的管理与挂载页（T9D 已实现）。需求侧三级消费流程：看题目 →（答不出）看标准答案 →（看不懂）展开资料讲解；本模块是第三级的供给侧。

含义与边界：

- **资产两态**：source（素材标准稿快照，入表即 active——素材已过两道人工门，挂载动作即人工发布决策）/ normalized（AI 多源归一稿，走完整状态机不校不上线；阶段二建设，登记见暂缓功能清单）。
- **快照语义**：content_md 是快照而非实时引用——源素材后续修改（重新入池 / 编辑标准稿）不影响已挂载资料，删素材也不影响快照存活（source_doc_id 保留溯源）；content_md 不可编辑、origin_type 不可改。
- **挂载管理**：手工挂载（目标 kp 非 retired、已挂载幂等）/ 摘除 / 排序与推荐语一次写回 / 归簇（挂后血缘回填归簇）；删除守护——零挂载才可删（防 C 端卡面展开悬空）。
- **血缘自动挂载（纯后端逻辑，无独立界面）**：成稿产出知识点（3.3）/ 候选并入已有知识点（3.2）时，成员候选的全部源文档自动资产化为 source 型 kp_doc 并挂载（kb.api.KbDocApi.attachLineage，按 origin=source + source_doc_id 幂等复用已有快照）；fail-soft——挂载失败只告警不阻断成稿主流程，是 pipeline 主动写 kb 数据的唯一通道。
- 题目↔资料多对多落 kp_doc_rel（UNIQUE 防重；origin lineage 血缘自动为主路径，embedding 建议与 manual 人工兜底）。

落点：后端 kb 包，拥有 kp_doc / kp_doc_rel 表；接口 `/api/admin/kp-doc`；KbDocApi 供 pipeline 血缘挂载调用。

### 3.6 校对流转（/admin/review-flow）

发布前最后一道人工门（T9 已实现）。成稿校对队列两段视图：「待校对」（kp_main draft）→ 校四样 → 通过转 reviewed；「待上线」（reviewed）→ 抽屉复核或列表行直接上线转 active。簇级草稿（draft 簇）逐个校对，语义同知识点。

含义与边界：

- **校四样（四项全勾才允许通过）**：技术正确性（参数、数字、因果链顺序，多源冲突已裁决）/ 评分要点可判定性 / 变体覆盖面 / 资料挂载合理性（血缘抽检、推荐语与排序核对，无挂载提示可去资料讲解页手工补）。
- 卡面预览复刻 C 端形态（题面钩子 / 三档样例 / 追问链 / 挂载资料）；来源标注（是否管道成稿）读 pipeline 成稿记录，跨模块聚合走前端，不新增后端跨模块读接口。
- approve 支持直通上线（同一校对会话内先过校对再落 active，"不校不上线"由准入校验保证）；changeStatus 严格逐步推进保留作程序化入口（页面实际都走 approve）。
- 复核到期时间随上线落 90 天，扫描与队列的自动化随二期（登记见暂缓功能清单）。

落点：后端 kb 包（approve 动作在 `/api/admin/kp` 与 `/api/admin/clusters`），页面读 `/api/admin/knowledge-map/compose/records` 做来源标注。

### 3.7 知识卡分享（/share/:kpId，公开页）

知识点的第四类消费方（T5/T9D 已实现）：用户在闯关卡面、抽卡结果、模拟考报告三处出口（共用同一套题卡结构）可把当前知识点生成分享卡——**卡图**（题面 + 难度五色 + 技能域标签 + 追问层数提示 + 产品水印，前端渲染）与**公开链接**（公开只读页，无需登录，接收者翻面看答案、展开追问链与资料讲解）。无 B 端管理界面。

含义与边界：

- 红线：卡与公开页只含库内容、绝不含个人数据；公开接口只输出 active 状态内容（非 active 统一 404）；公开页不渲染目标刻度（无个人职级）。
- 实现：kb 包无鉴权只读接口 `GET /api/share/kp/{kpId}`（题面、变体、难度、技能域、追问链、三档样例、簇引用与挂载资料 active 列表）与 `GET /api/share/doc/{id}`（资料讲解公开视图）；前端公共路由 `/share/:kpId` 不在 C/B 两棵树内（与 404 同级）。
- 零 LLM 调用；不做分享计数与接收端答题。

落点：后端 kb 包 ShareController / ShareDocController；公开接口属权限矩阵"公开"类（4.3）。

### 3.8 账号管理（/admin/accounts）

认证的 B 端侧（T1 已实现）。完全双表下本页管理的是后台人员（sys_staff）——客户账号不在这里，客户防滥用靠概览页用量监控，客户内容一律不看。

- 后台人员列表：用户名、角色（admin / editor）、创建时间、最近登录、状态。
- 新增账号：管理员为同事创建员工账号，指定初始口令与角色（admin / editor）——员工账号不经公开路径产生。
- 停用 / 启用：停用即后台会话失效并拒绝后台登录，是处理滥用与离职同事账号的第一个动作；启用恢复。
- 口令重置：v1 无找回密码（不接邮箱 / 短信服务），忘记口令走管理员重置（员工与客户两侧同此口径）。
- 边界：不做账号删除（停用即可，删除涉及个人数据清理策略，留待后续）；角色仅 admin / editor 两值固定，不做可配置的角色管理与权限矩阵——"谁能进后台、谁能动账号与配置"这一层区分就够，几人互信团队上 RBAC 是过度设计。

落点：后端 account 包（C 端侧见 2.7），接口 `/api/admin/accounts`（仅 admin），页面 /admin/accounts。

### 3.9 系统配置（/admin/settings）

运行参数的查看与调整入口（T2 已实现）：LLM 限额、模型路由等运行参数存 sys_config 表（归 llm 包拥有），B 端 /admin/settings 页读写，改动即生效，不写死在代码。

- 连通性自检与用量对照：系统配置页提供 provider 连通性检测与 llm_usage_daily 用量视图——B 端生产类入口不设限额不计熔断，用量观测是唯一的总量防线。
- 权限：本页接口仅 admin 角色可用（editor 不可见"系统"菜单组）。
- 边界：本页只管运行参数——provider 密钥不进设置页，只走运行目录 config/application-local.properties 或环境变量（见 4.3 涉密配置）；模块级技术职责（provider 屏蔽、成本治理、限额表）见 4.2。

## 四、无界面的共享模块

### 4.1 判定引擎

产品可信度的根。LLM 只做对齐判断、不做知识判断：评分要点是知识库里预制的尺子，判定引擎的唯一职责是把用户的自由回答对齐到尺子上，输出强制 JSON，判定规则全部写在代码里。

含义与边界：

- 三条硬规则：答况四分流（对/缺/错/空，判定驱动追问）；引用强制（命中要点必须附用户原话，引不出算未命中）；档位公式（LLM 从不碰分数）。
- **单知识点四档规则**（代码写死）：

| 档位 | 规则 |
|---|---|
| 优秀 | 必须要点命中 100% + 至少 1 个加分项 + 扛住全部追问层 |
| 良好 | 必须要点命中 100%，或 ≥80% 且全场无「错」 |
| 及格 | 必须要点命中 ≥60% 且无「错」 |
| 不及格 | 出现「错」，或命中 <60% |

  「错」是硬否决项——面试里说反概念的挂、讲得浅的过。带分级尺子的题型在此基础上有差异化：八股按「必须命中 + 加分项」的分级特例执行、设计演进链按命中要点的深度分布定档、项目叙事全部必须命中；差异化细则随判定引擎开发（T12）在开发计划任务节定稿。聚合：主问题 3 分 / 追问层 2 分；简历授权知识点 ×1.5，职级基线 ×0.8（参数放配置）。**加权及格率 → 四档总评**：≥85% 可上战场 / 70~85% 差强人意 / 50~70% 有硬伤 / <50% 缺口太大（total_grade 枚举：excellent/good/pass/fail）。**简历主张存活率** = 本场抽到的简历授权知识点里没被打穿的比例，连续两场 <50% 触发简历降级建议。**教练总评**：LLM 只写叙述和归因（元弱点、下周任务），不给分。
- 每次判定留**评分要点集的全量快照**（layer_key + level + 要点文本 + 命中与否 + 引用原话），不只存命中项——档位公式吃命中分布，全量快照才能在内容改版后重算历史档位。
- 判定范围以目标职级的停止点为界，停止点之下的层不参与档位计算。
- 降级路径：LLM 输出不合法 JSON 或超时（15s）重试一次，再失败解锁自评按钮——判定永远不是单点故障。
- 被模拟考与闯关的练习模式消费（闪卡快过与抽卡翻面自评不触发判定；抽卡里"橙红卡可选进入判定"复用闯关练习模式的判定流程，翻面自评本身不触发）；消费方少但规则是全局尺子，归属任何一方都会让规则随业务漂移，因此单列。判定模板（prompt 文本）归本包 resources，llm 模块只负责装载渲染；判定输出 JSON 契约见附录 A。

落点：后端 judge 包，拥有 answer_log 表（写入方，learning/exam 经 api 读取；attempt_id 为逻辑引用不做外键，跨包表耦合避免见附录 A）；依赖模型接入与知识库（读评分要点）。

### 4.2 支撑能力

三个无业务语义的技术模块。模型接入（llm）屏蔽 provider 差异：按用途路由模型（判定用便宜模型温度 0、总评用好模型）、装载 prompt 模板（模板文本归各业务模块，llm 只提供渲染入口）、校验返回 JSON、失败重试与降级，换模型服务商只改配置不改业务代码。**成本治理（默认限额可配置）**：按调用入口 × 天落库计数，入口分三层——高频判定类（练习模式判定、抽卡判定、模拟考逐问判定）、低频必要类（建档整理、叙事故事起草、教练总评、变体现场改写）、B 端人工触发类（拆题兜底、聚类去重、AI 成稿；前两层为 C 端消费类、第三层为 B 端生产类，限额口径分家见下）。默认限额：

| 入口 | 默认限额 | 超限动作 |
|---|---|---|
| 练习/抽卡判定（单用户） | 200 次/天（软上限，正常重度约 50 次） | 提示后可继续，当日计数异常告警 |
| 变体现场改写（单用户） | 20 次/天 | 回退预存变体原文 |
| 模拟考 | 1 场/天（attempt 落库即约束） | — |
| 单用户合计兜底（该用户名下全部档案 × 全部 LLM 入口合计） | 300 次/天（硬熔断） | 当日剩余调用全部走"AI 看不准，自评解锁"降级 |

**限额口径分家**：LLM 成本控制只落在**单用户维度**（用户账号 sys_customer，名下全部档案共享配额，不按档案各给一份）——上表各限额与单用户合计硬熔断即 C 端全部约束；B 端生产类入口（拆题兜底、聚类去重、AI 成稿、embedding，profile_id=0 哨兵）**不设限额、不计任何熔断**，用量经 llm_usage_daily 与系统配置页用量对照观测，B 端人工触发本身就是节流阀。原**全站每日总熔断取消**（多账号滥用的总量风险改由用量观测承担，公网出现异常流量时再评估恢复）；T2 已实现的全局开关降级为默认关闭的可选护栏（若启用仅统计 C 端消费类入口）。

限额与模型路由均为运行参数，B 端**系统配置页**（/admin/settings）读写（页面口径见 3.9），改动即生效；参数存配置表，不写死在代码。文档解析把 md/txt 变成干净纯文本并还原标题树，**建档的简历解析专用（T10 复用）；素材管道自 T6R 起不再使用解析前置步**——素材清洗与格式标准化并入 LLM 预处理重写（3.1），素材上传 v1 只收 md / txt 与图片资产（docx / pdf 由管理员前置转换为 md 后上传），扫描件口径随建档 T10 另定。到期调度只定时扫描**内容复核到期**，把过期内容推入人工复核队列，调度状态持久化在库里，重启不丢；复测与抽查到期均为查询推导（user_kp_state.due_at 实列 + 索引），不经调度器。**scheduler 随二期实现（登记见[暂缓功能清单](暂缓功能清单.md)）**：一期不建 scheduler 包、无定时任务，复核到期时间照常落库，靠 B 端知识点列表「复核是否到期」筛选人工巡检。

含义与边界：这三个模块不解释业务语义、不持有业务规则；换模型、换解析库、换调度方式，改动收敛在各自模块内。

落点：后端 llm / docparse / scheduler 包；被多个业务模块依赖，不反向依赖任何业务。系统配置页（/admin/settings）读写 llm 包拥有的配置表（限额、模型路由等运行参数），配置归属 llm、界面归 B 端；连通性自检与用量对照在系统配置页（已实现，T2）。**模型接入由 Spring AI 2.0 承载（T2 引入）**：用 OpenAI 兼容适配器把 provider 差异收敛在 base-url + api-key + 模型名三点，换服务商只改配置不改业务代码；provider 密钥只走运行目录 config/application-local.properties 或环境变量，不进库、不进设置页、不进 jar。

### 4.3 基础公共契约

已随 T0/T1 落地的契约，改动须在本文记录：

- **统一响应与错误体**：后端错误统一 `{ status, code, message }`，前端 `api/request.ts` 透传；业务异常走 BizException（validation / conflict / notFound 等工厂方法），SQLite 约束异常由 GlobalExceptionHandler 显式翻译成 4xx（CLAUDE.md 陷阱 B）。
- **常量组**：后端 `@ConstantGroup` 注解 + 启动扫描 + 内存注册表，公开接口 `GET /api/constants` 按组名下发 code/name；前端 constantsStore 消费，types.ts 类型联合做编译期校验；新增 LLM 入口（用途）在 LlmPurpose 枚举登记即自动进常量组。
- **权限矩阵**：轻量拦截器 + JWT + AuthContext（AuthContext.currentStaffId() / currentCustomerId()），刻意不引 Spring Security；接口树两棵——B 端 `/api/admin/**` 只认员工会话（sys_staff），C 端 `/api/**` 只认客户会话（sys_customer），两套会话互不通用；公开接口仅登录注册 / 常量下发 / 知识卡分享（`GET /api/share/kp/{kpId}` 与 `GET /api/share/doc/{id}` 无鉴权只读，仅输出 active）与素材图片流（`/api/admin/docs/{id}/source/**`，员工会话）。**新增接口必须先在本文或开发计划对应任务登记归属**（B/C 树 + 公开与否）。
- **测试基线**：Spring Boot Test（JUnit 5 + AssertJ + MockMvc），SQLite 独立测试库不 mock 数据层，`mvn test` 是合法验收命令；schema.sql 幂等（CREATE TABLE IF NOT EXISTS）。
- **涉密配置**：真实密钥只走运行目录 `config/application-local.properties`（模板 `.example` 入库），`src/main/resources` 不放任何密钥；测试 profile（test）与生产（prod）不加载 local。

## 五、依赖方向与红线

依赖关系（本节为包依赖真相源）：

- 建档 → 知识库（域/簇/考点菜单）、文档解析、模型接入；生成关卡 → 知识库、建档；闯关 → 判定引擎、知识库、生成关卡；抽卡 → 知识库、生成关卡（共享练习态，无编译依赖新增）；模拟考 → 判定引擎、知识库、profile（写降级建议）；复盘 → 知识库、learning（写信号、读练习态与虚报证据）、profile（写升降级建议）。
- 判定引擎 → 模型接入、知识库；内容管道（素材库 / 候选池 / 知识地图）→ 知识库、模型接入（解析职责已并入素材库的 LLM 预处理重写，不依赖 docparse，见 3.1）。
- 复盘信号回流到关卡重排的权重，走数据流而非编译依赖：复盘经 learning api 写 user_kp_signal（表归 learning），生成关卡在重排时消费——依赖方向 exam→learning 单向，依赖图无环。
- 账号认证（account）是支撑性模块：不依赖任何业务模块；profile → account（档案归属客户账号）；鉴权在 web 层横切且双树隔离——/api 接口只认客户会话（sys_customer），/admin 接口只认员工会话（sys_staff），两套会话互不通用；登录、注册、后台登录、知识卡分享为仅有的公开接口。
- 依赖图无环；跨模块只走对方的 api 包，repo 不出模块；web 层只依赖领域模块。

四条领域红线，任何模块的实现都不得违反：

1. 分是公式算的，LLM 从不碰分数；判定规则在判定引擎实现，不交给模型。
2. layer_key 是追问层的稳定身份，永不复用、永不修改，禁止用数组下标作身份。
3. 库/态分离：全局内容进 kp_*，个人数据进 user_*，用户独一无二的内容绝不进全局库表。
4. 不校不上线：未过人工校对的知识库内容不许进用户路径；库校对只重写内容，不碰用户进度。

### 7.3 判定输出 JSON 契约（judge → 消费方）

```json
{
  "verdict": "hit | shallow | wrong | blank",
  "next_action": "drill | rephrase | fallback | switch",
  "hits": [
    { "point_id": "string", "layer_key": "string", "level": "basic | mid | senior", "hit": true, "quote": "用户原话引用，未命中为 null" }
  ],
  "missing_summary": "教练口吻的一句话缺口描述"
}
```

约束：`hits` 为该次判定所用评分要点集的**全量**（含未命中项，hit=false）；schema 变更必须与 few-shot 样例同步改，防止模型输出漂移；要点 level 三级（basic/mid/senior）与职级五档（level 枚举）是两套刻度，字段命名有意区分。
