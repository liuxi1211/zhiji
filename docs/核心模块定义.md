# 知己 · 核心模块定义

> 这份文档是开发任务拆分的原子单位清单：每个模块一段，讲清概述、含义与边界。C 端与 B 端只是前端的页面组织（同一份构建产物，靠路由 `/` 与 `/admin` 区分），后端始终是一个单体工程，下列模块都是这个单体里平行的业务模块。上游产物是 [项目企划书](项目企划书.md)（产品流程与判定规则）、[知识库PRD](prd/知识库PRD.md)（内容资产与生产管道）。**现阶段只写需求 PRD，不建独立的研发设计文档**（《考点库设计》《系统架构设计》不再重建）：表归属与枚举契约以本定义附录 A 为准，包边界以本文第五节为准，字段级 DDL 以 kb 模块落 `schema.sql` 时为准。开发以本定义为基础逐模块进行；各业务域在开发前会像知识库一样抽出独立 PRD 详细完善（知识库PRD 为第一个范例），拍板决策的现行口径一律以三份核心文档为准（迁移规则见工程根 CLAUDE.md 开发工作流）。

> 命名口径（2026-09-22 拍板，去游戏化）：C 端组织结构统一叫**关卡制**——每个技能域一个**关卡组**，组内按主题簇分**关卡**；原设计过程中的"副本/塔/楼层/爬塔/Boss 战/新手村"等游戏化名词一律以本文口径为准。"抽卡"保留（用户认可的轻趣味入口，配简单翻牌动画）；积分、连击等游戏数值系统不引入，难度五色保留。

## 二、C 端模块

### 2.1 建档

用户进入产品的第一站，也是简历档案的管理入口。每个用户最多维护 3 份简历档案，档案是备考上下文的顶层归属：一份档案包含简历原件与解析文本、技能画像、备考计划、项目素材，生成关卡、闯关、抽卡、模拟考、复盘的个人态全部挂在档案下，切换档案即切换备考上下文，进度互不污染。建档动作发生在档案内：有简历就上传解析，没有简历就跟 AI 聊——年限、岗位、做什么、用过什么。AI 从简历和对话里整理出技能画像草案，用户逐条拍板：不熟的删掉、漏掉的加上、措辞不准的改掉。对话里聊到的项目细节（数字、冲突、结果）作为项目素材沉淀下来，后续成为项目叙事和模拟考追问的原料。

含义与边界：

- 产出四样东西：定稿的技能画像（user_skill）、目标职级（user_profile.level_target，CHECK 约束五档：初级/中级/高级/资深/专家）、备考计划（目标岗位/JD/周期/每日时间，user_plan）、项目素材（user_case），全部归属当前简历档案。目标职级是全链路的深度标尺：过关停止点、基础关卡组组成、模拟考下钻深度都由它推导；建档时用户明确说了就采用，没说就按工作年限推测缺省值，用户随时可改——32 岁面中级岗，全套按中级复习，完全合法。（年限→职级缺省映射表待定义，见第七节待办。）
- 无简历用户同样建档：对话收集年限、岗位、技术栈，档案形态为不含简历原件的默认档案，其余流程与有简历用户完全相同。
- 画像走状态机（草稿 → 确认 → 定稿），未定稿的画像不参与生成关卡。
- LLM 在这里只做整理与起草，事实由用户逐条确认；建档不答题、不摸底，入口永远没有考试。
- 简历主张的降级/升级建议写回触发它的那份档案，档案间互不串写。
- 不碰知识点内容，不碰练习进度。

落点：后端 profile 包，拥有简历档案实体；依赖技能库（画像候选项）、文档解析（简历抽文本）与模型接入（整理草案）。

### 2.2 生成关卡

基于档案内定稿画像与备考计划，把知识库裁成属于这份简历的一组组可打关卡。检索与组织分开：检索用技能条、项目素材、目标 JD 和**目标职级**去匹配知识点，决定哪些内容进关卡、权重多高；组织不按技能条（个人态，增删改名会抖动骨架），按知识库现成的「技能域 → 主题簇 → 知识点」结构展开为**关卡制**——每个技能域一个关卡组，组内按主题簇分关卡、关卡内按难度与前置拓扑排序；职级基线做成第一个「基础关卡组」（不分域的目标职级必问基础，靠前快速过）。先闯哪组用户自选（系统给默认序：基础关组 → JD 相关 → 库级频率信号 → 授权密度），全部关卡组完成 = 这份简历的知识库学完。跨域前置在学习地图上表现为锁：前置所在关卡组未完成到相应关卡，本组关卡上锁，防止跳跃式推进。

来源与权重不落库，全部消费时推导（企划书原意："聚合权重按两个字段推导，不单独存库"）：某知识点是否简历授权，由它是否匹配当前档案定稿画像的技能条推出，承载模拟考聚合权重 ×1.5 与简历主张存活率的定义域；是否职级必问（进基础关组），由目标职级的基线规则推出，承载权重 ×0.8；是否信号回流，由 user_kp_signal 反查得出。关卡数据只存关卡组与关卡的序列本身（顺序、前置锁），不存任何来源标记；放弃决策、过关状态等个人态统一写 user_kp_state（见 2.3），重开时按 user_kp_state 的放弃标记过滤关卡。

不进关卡的内容分两种。一种是未命中：画像授权、职级基线、JD 与个人信号都不指向的内容，天然不进，不展示也不留痕。另一种是显式放弃：用户在学习地图或闯关途中对关卡里的题手动点击放弃，它移出关卡组、进入放弃分区，原因可选填。放弃清单 v1 只由用户手动维护，系统不做自动标定（职级×时间预算的自动减法、算法手撕的预置放弃都不做，留到以后）；算法手撕在知识库范围外，学习地图上以一行静态说明提示替代方案（LeetCode），不做成数据。重新生成关卡保留用户的放弃决策，不重新计算。

含义与边界：

- 域与难度之争的取舍：关卡制让"域放在一起"（组内）与"难度递进"（关卡内）同时成立，牺牲的只是跨域全局难度递进——跨域难度本不可比，这个牺牲是干净的；跨域依赖用锁表达。
- 难度不是准入门槛，只是排序属性：进关的题集由四信号（画像授权、职级基线、JD、复盘信号）并集决定，任一命中即进，与难度无关；难度只决定关卡内的排序与卡面颜色。禁止任何"按用户职级过滤难度带"的逻辑（如高级只抽橙红卡）——那会结构性漏题：同一道题对不同目标职级的用户是同一道，差的只是过关深度（见 2.3 停止点）。
- 画像条目删除的语义是修正真实水平，不是决定不学：职级基线与 JD 信号不随删除消失（HashMap 对面中级岗的人必问，删了反而更需要练）；"不学"只发生在放弃分区的显式决策里。
- 核心动作是"裁"：每个知识点的具体内容不现场编，从预制知识库按需取用，点开才渲染；学习地图是独立页面，C 端日常主入口。
- 可重开：复盘信号回流、简历主张降级之后重新生成关卡；重生成只重写关卡组与关卡（user_path），练习进度（user_kp_state）原地不动，闯关游标按新序列与掌握状态重新定位。

落点：后端 learning 包（与闯关、抽卡同包，开发任务独立），产出挂在简历档案下；依赖知识库（读知识点、难度、前置、域与簇）、建档（读定稿画像）、复盘（消费个人信号，走数据回流，见第五节）。

### 2.3 闯关

日常主体。学习地图上选一个关卡组进入闯关页，任务是完成这个关卡组：从当前关卡继续往前，组末即该域完成。闯关不设"每日抽卡"，去哪个组、闯几关完全由用户自控，没有随机调度。

每个关卡就是一张闪卡题组：初始只展示题目，用户先回忆，再翻面看标准答案；有更深一层的关联题目（追问）就展示入口；看不懂展开知识簇看从零详解；还不懂，后续版本针对这道题与 AI 对话交流。过关方式两种节奏并存、用户自选：闪卡快过——翻面自评「过了」直接往前（想快速过一轮拿印象的人）；练习模式扎实过——闭卷打字作答（语音转写二期接入，决策清单 D4），先作答才解锁自评，作答经判定引擎驱动下一步（继续下钻、同层换角度再问、回退前置知识点），答过才算判定过关。卡面上「我不会」与「我会，跳过」合并为过关选择：标了"不会"的卡进抽卡的弱点加权与复测队列；不想要的题可点击放弃，移出关卡组进放弃清单。

含义与边界：

- **快过与练习的双轨口径（决策清单 D1 已拍板）**：闪卡快过算过关推进，但在 user_kp_state 上单独落"快过态"标记（区别于"练习判定过关"）；快过态的卡同样进入抽卡验伪范围——抽查池对快过态卡上调抽中概率，与"我会，跳过"的抽查同等对待，虚报同样打回复测队列。即：快过是显式的低保障通道，挤水机制延伸覆盖它。关卡过关按"快过或练习任一过关"计，但报告与存活率只统计练习判定的数据。
- 闯关纯推进、组内不回头：复测与复习全部交给抽卡模块，闯关只负责向前——两个功能互不打扰，节奏各自干净。判定动作里的"回退前置知识点"是内容层回退（就地展开前置知识点的从零讲/闪卡），不改变闯关游标。
- 练习模式不设场次实体：逐关作答逐关判定，attempt 仅模拟考使用（练习作答的判定历史 attempt_id 为空）。练习模式未过关（答况为错/空且变体再问仍不过）的关卡留在当前关，引导先看前置知识点或从零讲，下次进组从该关继续；用户可随时切闪卡快过。
- 同一道题，不同目标职级过关深度不同：过关标准由知识点的职级要求（下钻停止点）决定——面中级答到第 1 层算过关，面资深要扛到第 3 层；停止点之下的更深追问层照样可见（学无止境），但目标刻度明确标注"到你目标职级讲到第 N 层算够"。同一关卡组对不同用户是不同题集（四信号裁剪）+ 相同题目、不同尺子（停止点）。
- 漏题的三道防线：并集准入（不做难度/职级过滤）；复盘兜底（真被问到的题不在组里，录题回流下次生成进组）；标定进校对清单（职级基线与停止点的完整性是内容管道人工校对的必检项，见 3.3）。
- 关卡即题组，重玩成本低：单关 3 分钟量级，随时进来随时闯，进度就是"闯到第几关"，不需要每日任务感。
- 过关选择里"不会"是抽卡的输入信号（弱点加权 + 复测队列），"我会，跳过"进抽查池由抽卡验伪——自报水分的挤压器在抽卡侧。
- 卡面按知识点难度配五色：难度约定为 1~5 整数档，与白/绿/黄/橙/红五色一一对应（1 最易、5 最难）。闯关、学习地图、抽卡共用同一套难度配色；颜色只编码难度，简历授权等来源信息用角标区分，不抢颜色语义。
- 题卡内容映射，闯关、抽卡、模拟考三处共用同一套卡结构：正面 = 题面（练习与模拟考中按问法变体或现场改问法呈现）；背面 = 标准回答样例，默认展开及格档，良好/优秀两档可展开；追问入口 = 追问链，按 layer_key 逐层展开；看不懂 = 展开主簇的从零讲；目标刻度 = 该知识点职级要求按当前目标职级渲染出的停止点（「讲到第 N 层算够」）。评分要点只进判定引擎，不上卡面。
- 关卡与过关口径：关卡 = 主题簇，关卡过关 = 关卡内全部知识点过关，到组末即全组完成；过关选择（过了 / 不会 / 我会，跳过 / 放弃）与练习模式判定结果统一写 user_kp_state——它是闯关游标、抽卡卡池与三条抽卡信号的共同数据源，抽卡卡池即 user_kp_state 中已过关知识点的集合。放弃决策同样落 user_kp_state 标记位（见 2.2），重新生成时，放弃的知识点不进组、进放弃分区。
- 项目叙事的练习（看标准故事 → 练习模式作答，讲 3 分钟的口述形态随语音转写二期接入）归这里；标准故事由档案内建档素材起草，六要素组织，每个数字和事实逐条经用户确认。叙事卡的库侧承载是 sub_type=narrative 的模板知识点（题面模板 + 指标清单评分要点，不含任何个人内容），个人标准故事挂 user_narrative 并关联模板知识点与档案，多项目按 project_name 区分——库/态分离在叙事题型上的落地。

落点：后端 learning 包，状态挂在简历档案下；依赖判定引擎（仅练习模式与模拟考消费）、知识库、生成关卡（关卡序列与练习态分表，重新生成不动练习进度）。

### 2.4 抽卡

随机学习与随机检验的轻量入口，全部复习机制在这里，也是**每日回访的默认锚点**（决策清单 D3 已拍板：不建每日卡与任务系统，"今晚先抽一把"就是打开产品的理由，支持全随机或指定域连抽——单抽/3 连，配简单翻牌动画，适合碎片时间）。卡池 = 已闯过关卡里的卡（闯关走过的部分），按三条信号混抽：SM-2 到期的复测卡（间隔重复的主引擎）、抽查池到期的验伪卡（闯关时标「我会，跳过」以及快过态的卡，低频弹出翻面复验，虚报打回复测队列并累积虚报证据）、闯关时标「我不会」的弱点卡（抽中权重上调）。抽卡既是复习器也是自报水分的挤压器，闯关因此可以放心纯推进。

抽卡体验轻：翻面自评为主，橙红高难卡可选进入判定（想要真检验时用，复用闯关练习模式的判定流程）；趣味性保留翻牌动画与连抽，不引入积分、连击等游戏数值系统，不设正式报告。

混抽权重按会话状态动态调整，第一版就要有：连对降权与低难度穿插卡。连续答对的卡在随机混抽中下调抽中概率（只调概率，不碰 SM-2 到期队列与抽查池的入场资格，权重设下限不为零——"变没"交给间隔重复去做）；连续答错达到阈值时，后续抽卡掺入少量已过关的低难度卡（难度 ≤ 2，对应白绿卡面），重建正反馈与掌控感。两者互补关系：SM-2 管"错的卡间隔重置后回来"，低难度穿插卡管"连错时当场给正反馈"；穿插卡作答结果照常写 SM-2 参数，就是一次正常复习，不产生额外状态。连对/连错计数落 user_kp_state 实列标记位（内部状态，不做 UI 展示），不加表。

含义与边界：

- 三条抽卡信号（到期复测、抽查验伪、弱点加权）都由闯关的过关选择喂养，抽卡不自己产生新任务：闪卡自评、练习判定、抽查复验都更新 user_kp_state 的 SM-2 复习参数与标记位（弱点标记、抽查池状态、虚报证据计数、快过态标记），字段随详设定稿。SQLite 纪律（CLAUDE.md 陷阱 E）：SM-2 的下次到期时间 due_at 必须实列化并建索引 `(profile_id, due_at)`——抽卡按 due_at 过滤是日常高频查询，不能埋进 JSON；easiness/interval/reps 等非查询参数可存 JSON；连对/连错计数、虚报证据计数同为实列标记位。
- 指定域抽卡天然支持考前抱佛脚：明天面 ES，今晚连抽 ES 组。
- 抽卡数据（复测通过、虚报证据）回流影响两个下游：弱点卡决定抽中权重，简历授权卡的虚报/失败累积汇入复盘的降级建议。

落点：后端 learning 包，与闯关共享练习态；依赖知识库、生成关卡（界定可抽卡池）。

### 2.5 模拟考

复习好了来一套的全真检验：**全套真实模拟考**（决策清单 D10 已拍板：不再分级入场——原"分域检验"的职能由抽卡承担，指定域抽卡 + 橙红卡进判定就是按域的即时检验），**每天一次机会**（attempt 按天限一次，防高频刷考烧判定成本），有时间限制、有评分、出题规则贴近真实面试。入场不设通关解锁——组卷范围由四信号（画像授权、职级基线、JD、复盘信号）与库级频率信号推导，不依赖闯关进度，"考前一周没资格考"的结构性冲突不存在。方向轮转组卷（先横切再纵深），每答一问判一次、判定驱动追问（对则下钻、缺则继续钻、错则温和纠正后同层换角度、空则切题），考完出三样东西：加权及格率（映射四档总评：优秀/良好/及格/不及格）、简历主张存活率、教练总评（LLM 只写叙述与归因，不给分）。

含义与边界：

- 简历主张存活率 = 本场抽到的简历授权知识点里没被打穿的比例（授权由画像匹配推导）；连续两场低于 50% 自动触发简历降级建议——"简历和知识库互相改"的量化落点。降级建议与存活率机制一期保留，对用户可见；呈现细节（建档说明页、教练措辞、一键驳回）二期打磨（决策清单 D7），写回触发它的档案走 profile 模块 api。
- 判定的同步/异步：练习模式同步判定（等判定回来驱动追问）；模拟考作答流与判定流并行——判定回来才出追问，等待期 UI 明示"面试官在记录"，考试计时只计作答时长，判定超时（15s）不扣作答时间；最终评分（加权及格率/存活率/教练总评）异步生成。超时与非法 JSON 同走"重试一次→降级自评"。
- 判定可申诉（决策清单 D6 已拍板，v1 做"标记申诉"折中方案）：口误、用词不准等可纠正判定，结果页固定"我有异议"入口，点开可见该次判定引用的用户原话，一句话提交标记。标记后该判定进人工复核队列（复核在 B 端校对流转页进行，见 B端管理台PRD 第八节），复核确认后手动改判为"不计入档位"——v1 不做 AI 自动改判，救济通道从第一天存在，改判权留在人手里（机制定义见知识库PRD 6.6）。
- 中途喊停的场次照常出报告，标"未完成不评级"；连着两场喊停，考前说明里给提醒。
- 设计演进链以演进链形态进模拟考，平行方向乱序抽层防背题；未覆盖方向进下次优先队列，覆盖度进报告。
- 跨场趋势（断在第几层、扛了几层、深度分布演变）比单场评级值钱。

落点：后端 exam 包；依赖判定引擎、知识库、profile（写降级建议，走 api）。组卷不依赖闯关进度，learning 依赖随之取消（D10 拍板的附带简化）。

### 2.6 复盘

真去面了，回来把被问到的题录进去。能对上已有知识点的，写成个人复盘信号（权重最高的频率信号），作为最高权重输入供关卡重排消费；对不上的，进知识库候选池，成为知识库的生长点。同时触发它的那份档案里，路径和简历跟着更新：练不住的主张从简历降级，练深了的知识点反过来写成简历亮点。

含义与边界：

- 体量小、杠杆大：五环节里唯一由真实面试驱动的环节，也是"知识库不是建完的，是长出来的"这句话的入口。
- 个人复盘信号与库级频率信号分开存放：前者是隐私资产、随面试次数累积；后者是公共信号，只含面经信号与人工标定。
- 录题匹配知识点的前提是 C 端能搜到知识点：需要按题面模糊检索 active 知识点的搜索接口（接口清单随各后端模块落地时定义，口径见第六节对照表）；匹配由用户确认，不做 AI 静默归并——归并错了会污染权重最高的个人信号。
- 与模拟考同属 exam 包，但作为独立开发任务，因为它横跨"录题回流"与"简历升降级"两条链路。

落点：后端 exam 包；依赖知识库（知识点匹配与候选池）、learning（写 user_kp_signal，走 learning api）、profile（写升降级建议，走 api）。**user_kp_signal 表归 learning 包拥有**（决策清单 D9 已拍板）：复盘经 learning api 写入信号，生成关卡在重排时直接读本模块表——依赖方向 exam→learning 单向，依赖图无环。

### 2.7 账号认证

定位调整（决策清单 D16）后的新模块：产品首版即以小规模公开服务运行（腾讯云部署，经 CSDN / 小红书引流），注册登录从"将来再说"变成硬前置——陌生用户上传的是真实简历，数据隔离与口令保护缺一不可。账号结构为**完全双表双入口**（决策清单 D18）：客户（sys_customer）与后台人员（sys_staff）分表、分登录入口、两套会话互不通用。

- **注册**：用户名 + 口令 + 图形验证码，开放注册，写 sys_customer——低门槛承接引流转化，不做邀请码（与发帖引流的目的冲突）；不接短信 / 邮箱验证（"v1 不引外部服务"的既定原则），脚本防御靠验证码、注册与登录接口限流、全站每日 LLM 总熔断三道闸。注册成功即创建默认简历档案（2.1 的无简历档案形态），直接进建档。
- **登录与会话**：口令散列存储；C 端登录入口与后台登录入口完全分开，两套会话互不通用——客户 token 进不了 /admin 接口，员工 token 进不了 C 端 /api 接口；会话方案（JWT 或服务端 token）随实现定，PRD 不锁。未登录可达页仅五个：C 端登录 / 注册、后台登录、知识卡分享公开页 `/share/:kpId`、404。
- **数据归属**：档案归属客户账号（sys_customer），账号 1 : 档案 ≤3；历史单机数据迁移 = 你的练习档案归入你自己注册的客户账号。
- **内部协作账号**：几位同事以内容维护者（editor）身份参与题库生产（决策清单 D17），员工账号由管理员在后台创建（走 sys_staff，不经公开路径，初始口令线下交付；后台登录入口不做公开引流）。双表分立（D18）意味着员工账号与客户账号互不相通：同事要试用 C 端，另行注册客户账号。
- **v1 边界**：无找回密码（员工与客户两侧都走管理员后台重置）、无第三方登录、无邮箱验证、无注销账号（停用即可）；记住我、修改口令随后续版本。
- **成本与滥用防线**：D12 按档案限额对每个客户账号生效；sys_config 新增全站每日 LLM 总熔断运行参数；概览页提供用量视图与异常监控（见 B端管理台PRD 第三节）。

落点：后端 account 包，拥有 sys_staff / sys_customer 两表；被 profile 依赖（档案归属客户账号）；C 端登录 / 注册、后台登录、知识卡分享为仅有的公开接口；/api 接口只认客户会话，/admin 接口只认员工会话（web 层横切，两棵接口树各自校验、互不认对方 token，D18）。

## 三、B 端模块

### 3.1 技能库

全局一份的技能域字典。它有三重身份：建档时技能画像逐条拍板的候选项（用户从中认领或补充，形成个人画像）；知识库里知识点分域的归属依据；简历主张与知识点之间的授权锚点——画像条目经由技能域关联到知识点，主攻层"简历上写了的"由此成立，简历主张存活率也以它为锚。

含义与边界：

- 字典是内容资产，不随用户变化；B 端维护，C 端只读。
- 归属判断：它是三处消费的字典，塞进任何业务模块都会造成反向依赖，因此独立成模块。
- 简历的项目部分不在这里承载——项目素材在建档采集，六要素模板在知识库，见 2.1 与 3.2。

落点：后端 skill 包，拥有 skill_domain 表；被建档、知识库、生成关卡依赖。页面详设（增删改、排序、停用不删除）见 B端管理台PRD 第四节。

### 3.2 知识库

产品的核心资产，全局一份，存的是结构化的"面试怎么问、怎么判"：知识点（题面、问法变体、叙述框架、追问链带层身份与方向、分级评分要点、职级要求与下钻停止点、难度、前置知识点、主主题簇）、主题簇（从零讲与完整参考方案的生产共享单位）、前置依赖（学习维度，可跨簇，多数 0~2 个不硬凑）、库级频率信号（面经信号与人工标定）。

含义与边界：

- 命名口径：本模块与全库统一叫**知识库**——原子单元是知识点，主题簇、前置依赖、追问层、评分要点全部围绕知识点组织；"题库"这个词只留给竞品语境（刷题网站的题库、市面上的题库工具），面向用户的题面、题卡、考题等"题"字表述不受影响。
- 题型收敛为一类知识点（type 单值），差异下沉到 sub_type 枚举：default / design_chain / narrative（枚举契约见附录 A）；全局骨架（如项目叙事的六要素模板）也放这里，全局一份。
- 每条内容必须过状态机（draft → reviewed → active），不校不上线；上线后有复核到期机制，过期内容回人工复核队列。
- 库/态分离是根基：知识库只回答"有哪些知识点、结构是什么"，不感知任何用户。
- 概念边界最值钱也最容易守错：追问层是知识点的内嵌结构（layer_key 永不复用），主题簇是生产单位，前置依赖是学习维度，难度与职级要求互不推导，三者两两正交。
- 字段约定：难度为 1~5 整数档（对应卡面五色）；每个追问层必须标所属方向 dir，主问题层方向固定为 main，方向是模拟考横向轮转与覆盖统计的分组键；追问链编辑只许改文本与顺序，层的增减走「新增层 / 停用层」，停用层的 layer_key 不得再分配给新层——这是红线 2 的操作化。
- 内容格式：讲解类字段（从零讲、完整参考方案、叙述框架、三档样例）为 Markdown 白名单（代码高亮 / 表格 / Mermaid），判定链路字段（题面、追问层、评分要点）保持纯文本（知识库PRD 4.7）。
- 簇先于知识点存在（kp_main 挂且只挂一个主簇，外键决定建簇在前）：建簇入口两处——管道聚类环节按素材聚簇加人工确认、B 端知识库页手工建簇/改簇/合并簇；簇级内容（从零讲、完整参考方案）与知识点走同一套状态机。
- **知识卡分享（决策清单 D14 已拍板）**：知识点的第四类消费方。用户在闯关卡面、抽卡结果、模拟考报告三处出口（共用同一套题卡结构）可把当前知识点生成分享卡——**卡图**（题面 + 难度五色 + 技能域标签 + 追问层数提示 + 产品水印，前端渲染）与**公开链接** `/share/:kpId`（公开只读页，无需登录，接收者翻面看答案、展开追问链与从零讲）。红线：卡与公开页只含库内容、绝不含个人数据；公开接口只输出 active 状态知识点；公开页不渲染目标刻度（无个人职级）。实现：kb 包加一个无鉴权只读接口 `GET /api/share/kp/{kpId}`（输出 active 知识点的公开视图：题面、变体、难度、技能域、追问链、三档样例、簇与从零讲引用），前端公共路由 `/share/:kpId`（不在 C/B 两棵树内，与 404 同级）；零 LLM 调用、不新增表，v1 不做分享计数与接收端答题。需求细节见知识库PRD 7.5。

落点：后端 kb 包，拥有 kp_cluster / kp_main / kp_prereq / kp_freq_signal 表；B 端 /admin/kp 同时管簇与知识点（建簇、合并簇、校对流转、复核队列）；被生成关卡、闯关、抽卡、模拟考、判定引擎依赖。B 端维护操作的详设（编辑约束、下线与合并不物理删除、前置防环、复核到期处理）见 B端管理台PRD 第五节。

### 3.3 内容管道

知识库的供应链。七环节：采集素材（面经、GitHub 仓库、CSDN 帖子、官方手册、书籍等，解析后双轨取用：频次信号 + AI 重写的参考输入，原文不直接进库）→ 文档解析与拆题（形态识别路由：题库型题-答配对 / 资料型章节切分 + AI 反推出题 / 面经型抽题供信号，先人工核对解析预览，三条路径汇成统一候选条目）→ 同题归一与地图（语义聚合为归一题，多源问法归一为变体候选、覆盖源数转频率信号；映射不上的进语料簇——确认后成正式簇，簇是知识点入库的前置；地图产出覆盖率视图，决定按簇建设顺序）→ 按簇成稿（多源答案交叉验证、追问链收割源题库递进设计、变体从多源问法收敛，过结构校验防键名漂移）→ 人工校对（技术正确性含多源冲突裁决、评分要点可判定性、变体覆盖面、从零讲的比喻）→ 入库上线（状态流转，频次信号含覆盖源数）→ 持续演化（复盘信号与新题库语料双生长点，已建设知识点增量吸收新来源）。

含义与边界：

- 版权红线：解析出的素材文本只是 AI 重写的输入，成品必须经重写加人工校对，保留参考出处（链接或书名 / 手册章节）；解析文本只留在素材文档里，不进知识点内容。
- 去重是生命线：管道里语义匹配加人工确认，入库时唯一约束再兜一道；同一知识点重复入库会稀释练习时间、分裂判定数据。
- v1 可以极简实现（手工录题 + AI 辅助成稿），但模块边界与"不校不上线"的安全线从第一天就有——知识库不会自己长出来，这条管道决定内容质量的上限。

落点：后端 pipeline 包，拥有 kp_candidate / kp_canonical / kp_source_doc 表；依赖知识库、模型接入、文档解析。B 端操作面详设（批量导入、形态路由与三路拆分、同题归一与知识地图、统一待办中心）见 B端管理台PRD 第六至九节；多源素材入库与语料先行三段式建设场景在第六、九节专项展开。

### 3.4 账号管理

认证的 B 端侧（决策清单 D16-D18）。完全双表下本页管理的是后台人员（sys_staff）——客户账号不在这里，客户防滥用靠概览页用量监控，客户内容一律不看。

- 后台人员列表：用户名、角色（admin / editor）、创建时间、最近登录、状态。
- 新增账号：管理员为同事创建员工账号，指定初始口令与角色（admin / editor）——员工账号不经公开路径产生。
- 停用 / 启用：停用即后台会话失效并拒绝后台登录，是处理滥用与离职同事账号的第一个动作；启用恢复。
- 口令重置：v1 无找回密码（不接邮箱 / 短信服务），忘记口令走管理员重置（员工与客户两侧同此口径）。
- 边界：不做账号删除（停用即可，删除涉及个人数据清理策略，留待后续）；角色仅 admin / editor 两值固定，不做可配置的角色管理与权限矩阵——"谁能进后台、谁能动账号与配置"这一层区分就够，几人互信团队上 RBAC 是过度设计。

落点：后端 account 包（与 2.7 同包），页面详设见 B端管理台PRD 第十一节；sys_staff 表归 account。

## 四、无界面的共享模块

### 4.1 判定引擎

产品可信度的根。LLM 只做对齐判断、不做知识判断：评分要点是知识库里预制的尺子，判定引擎的唯一职责是把用户的自由回答对齐到尺子上，输出强制 JSON，判定规则全部写在代码里。

含义与边界：

- 三条硬规则：答况四分流（对/缺/错/空，判定驱动追问）；引用强制（命中要点必须附用户原话，引不出算未命中）；档位公式（优秀/良好/及格/不及格由命中分布确定性算出，LLM 从不碰分数）。
- 每次判定留**评分要点集的全量快照**（layer_key + level + 要点文本 + 命中与否 + 引用原话），不只存命中项——档位公式吃命中分布，全量快照才能在内容改版后重算历史档位（与知识库PRD 6.5 同口径）。
- 判定范围以目标职级的停止点为界，停止点之下的层不参与档位计算。
- 降级路径：LLM 输出不合法 JSON 或超时（15s）重试一次，再失败解锁自评按钮——判定永远不是单点故障。
- 被模拟考与闯关的练习模式消费（闪卡快过与抽卡翻面自评不触发判定；抽卡里"橙红卡可选进入判定"复用闯关练习模式的判定流程，翻面自评本身不触发）；消费方少但规则是全局尺子，归属任何一方都会让规则随业务漂移，因此单列。判定模板（prompt 文本）归本包 resources，llm 模块只负责装载渲染；判定输出 JSON 契约见附录 A。

落点：后端 judge 包，拥有 answer_log 表（写入方，learning/exam 经 api 读取；attempt_id 为逻辑引用不做外键，跨包表耦合避免见附录 A）；依赖模型接入与知识库（读评分要点）。

### 4.2 支撑能力

三个无业务语义的技术模块。模型接入（llm）屏蔽 provider 差异：按用途路由模型（判定用便宜模型温度 0、总评用好模型）、装载 prompt 模板（模板文本归各业务模块，llm 只提供渲染入口）、校验返回 JSON、失败重试与降级，换模型服务商只改配置不改业务代码。**成本治理（决策清单 D12 已拍板，默认限额可配置）**：按调用入口 × 天落库计数，入口分三层——高频判定类（练习模式判定、抽卡判定、模拟考逐问判定）、低频必要类（建档整理、叙事故事起草、教练总评、变体现场改写）、B 端人工触发类（拆题兜底、聚类去重、AI 成稿）。默认限额：

| 入口 | 默认限额 | 超限动作 |
|---|---|---|
| 练习/抽卡判定（单档案） | 200 次/天（软上限，正常重度约 50 次） | 提示后可继续，当日计数异常告警 |
| 变体现场改写（单档案） | 20 次/天 | 回退预存变体原文 |
| 模拟考 | 1 场/天（attempt 落库即约束） | — |
| 全局兜底（单档案全部 LLM 入口合计） | 300 次/天（硬熔断） | 当日剩余调用全部走"AI 看不准，自评解锁"降级 |

另设**全站每日 LLM 总调用熔断**（决策清单 D16，公开服务防滥用）：所有账号合计达到上限即当日全面降级——C 端剩余调用走"自评解锁"，B 端人工触发类暂停，次日恢复；上限为运行参数存 sys_config，与下述限额同在系统配置页调整。

限额与模型路由均为运行参数，B 端**系统配置页**（/admin/settings）可调整，改动即生效；参数存配置表（llm 包拥有），不写死在代码。文档解析（docparse）把 pdf/doc/docx/md/txt 变成干净纯文本，建档的简历解析与内容管道的素材解析共用同一能力；扫描件明确报错不静默。到期调度（scheduler）只定时扫描**内容复核到期**（知识库PRD 8.3），把过期内容推入人工复核队列，调度状态持久化在库里，重启不丢；复测与抽查到期均为查询推导（user_kp_state.due_at 实列 + 索引），不经调度器。

含义与边界：这三个模块不解释业务语义、不持有业务规则；换模型、换解析库、换调度方式，改动收敛在各自模块内。

落点：后端 llm / docparse / scheduler 包；被多个业务模块依赖，不反向依赖任何业务。系统配置页（/admin/settings）读写 llm 包拥有的配置表（限额、模型路由等运行参数），配置归属 llm、界面归 B 端；页面详设（连通性自检、用量对照）见 B端管理台PRD 第十节。**模型接入由 Spring AI 2.0 承载（T2 引入，决策清单 D28）**：用 OpenAI 兼容适配器把 provider 差异收敛在 base-url + api-key + 模型名三点，换服务商只改配置不改业务代码；provider 密钥只走 application.yml / 环境变量，不进库、不进设置页。

## 五、依赖方向与红线

依赖关系（本节为包依赖真相源）：

- 建档 → 技能库、文档解析、模型接入；生成关卡 → 知识库、建档；闯关 → 判定引擎、知识库、生成关卡；抽卡 → 知识库、生成关卡（共享练习态，无编译依赖新增）；模拟考 → 判定引擎、知识库、profile（写降级建议）；复盘 → 知识库、learning（写信号、读练习态与虚报证据）、profile（写升降级建议）。
- 判定引擎 → 模型接入、知识库；内容管道 → 知识库、模型接入、文档解析、判定引擎（读判定聚合，暴露评分要点质量问题）。
- 复盘信号回流到关卡重排的权重，走数据流而非编译依赖：复盘经 learning api 写 user_kp_signal（表归 learning，决策清单 D9 已拍板），生成关卡在重排时消费——依赖方向 exam→learning 单向，依赖图无环。
- 账号认证（account）是支撑性模块：不依赖任何业务模块；profile → account（档案归属客户账号）；鉴权在 web 层横切且双树隔离——/api 接口只认客户会话（sys_customer），/admin 接口只认员工会话（sys_staff），两套会话互不通用（D18）；登录、注册、后台登录、知识卡分享为仅有的公开接口。
- 依赖图无环；跨模块只走对方的 api 包，repo 不出模块；web 层只依赖领域模块。

四条领域红线，任何模块的实现都不得违反：

1. 分是公式算的，LLM 从不碰分数；判定规则在判定引擎实现，不交给模型。
2. layer_key 是追问层的稳定身份，永不复用、永不修改，禁止用数组下标作身份。
3. 库/态分离：全局内容进 kp_*，个人数据进 user_*，用户独一无二的内容绝不进全局库表。
4. 不校不上线：未过人工校对的知识库内容不许进用户路径；库校对只重写内容，不碰用户进度。

| kp_cluster | kb | 主题簇：从零讲与完整参考方案，含状态机与复核到期；draft 态兼作语料聚合簇（知识地图确认后推进，D21） |

| answer_log | judge | 判定历史：全量要点快照（layer_key+level+文本+命中+引用）、答况、申诉状态（D6）、attempt_id（逻辑引用，不做外键） |

### 8.2 枚举真相源（前后端 CHECK / types.ts 对齐）

| 枚举 | 取值 | 说明 |
|---|---|---|
| sub_type | `default` / `design_chain` / `narrative` | 题型；type 单值知识点，差异下沉到 sub_type |
| verdict | `hit` / `shallow` / `wrong` / `blank` | 答况四分流：对/缺/错/空；"空"是独立值，不用空内容代替 |
| next_action | `drill` / `rephrase` / `fallback` / `switch` | 下钻 / 同层换角度 / 回退前置（内容层回退，不动闯关游标）/ 切题 |
| level | `junior` / `mid` / `senior` / `staff` / `expert` | 目标职级五档：初级/中级/高级/资深/专家 |
| total_grade | `excellent` / `good` / `pass` / `fail` | 四档总评：优秀/良好/及格/不及格（语义阈值见企划书 §四） |
| content_status | `draft` / `reviewed` / `active` / `retired` | 内容状态机；retired 保留被合并指向 |
| appeal_status | `none` / `marked` / `excluded` | 判定申诉状态：未申诉 / 已标记异议（进人工复核队列）/ 复核后不计入档位（D6 拍板的 v1 标记申诉） |
| staff_role | `admin` / `editor` | 后台人员角色：管理员（全权，含账号管理与系统配置）/ 内容维护者（B 端内容维护页 + 概览）；固定两值不做可配置角色（D18） |
| account_status | `active` / `disabled` | 账号状态：正常 / 停用（停用即对应侧会话失效并拒绝登录；员工 / 客户两表同构，D16/D18） |
| source_doc_status | `pending` / `parsed` / `parse_failed` / `split` | 素材文档状态机：待解析 / 解析成功待拆题 / 解析失败 / 已拆题入池（B端管理台PRD 6.2） |
| candidate_status | `pending` / `matched` / `converting` / `converted` / `merged` / `discarded` | 候选条目状态机：待研判 / 已研判待成稿 / 成稿中 / 已转化入正式库 / 已并入为目标知识点变体 / 已放弃（B端管理台PRD 7.1） |
| canonical_status | `pending` / `confirmed` / `built` | 归一题状态：AI 聚合待确认（低置信）/ 人工确认入图 / 已按簇建设成知识点（D21） |
| answer_src | `text` / `voice` | 作答来源：打字 / 语音转写；voice 随语音二期（D4）启用 |
| llm_purpose | `judge_practice` / `judge_gacha` / `judge_exam` / `profile_draft` / `narrative_draft` / `exam_summary` / `variant_rewrite` / `split_fallback` / `cluster_dedup` / `ai_compose` / `embedding` | LLM 调用入口（用途）：模型路由与限额以它为键，业务只认用途不认模型名（4.2 成本治理；T2 落地，Spring AI 2.0） |

### 8.3 判定输出 JSON 契约（judge → 消费方）

```json
{
  "verdict": "hit | shallow | wrong | blank",
  "next_action": "drill | rephrase | fallback | switch",
  "hits": [
    { "point_id": "string", "layer_key": "string", "level": "basic | mid | senior", "hit": true, "quote": "用户原话引用，未命中为 null" }
  ],
  "missing_summary": "教练口吻的一句话缺口描述"
}
```

约束：`hits` 为该次判定所用评分要点集的**全量**（含未命中项，hit=false）；schema 变更必须与 few-shot 样例同步改，防止模型输出漂移；要点 level 三级（basic/mid/senior）与职级五档（level 枚举）是两套刻度，字段命名有意区分。
