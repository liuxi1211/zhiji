# 知己 · 技能库 PRD

> **定位声明**：本文是技能条目组装与授权模型的域 PRD，回答三个问题：简历技能条目怎么组装（段型骨架与渲染规则）、组装结果挂什么（知识库簇，授权锚点）、怎么驱动练习与检验（强度承诺、升降级建议）。库侧范围只有域字典（skill 包，T3）；画像条目是个人态（profile 包，T10 消费）；挂载对象是知识库簇（kb 包，只读）。**知识结构只有一份真相源：知识库的「域 → 簇 → 知识点」**——技能库不再建第二份内容资产（拍板记录见 1.4，决策清单 D26）。上游口径见 [核心模块定义](../核心模块定义.md) 3.1 / 2.1 与 [B端管理台PRD](B端管理台PRD.md) 第四节；本文评审定稿后按第九节回改清单同步核心文档。另：域 PRD 统一收口 `docs/prd/` 目录（决策清单 D25），复杂需求先抽域 PRD 再开发。

## 一、需求背景

### 1.1 简历能力区的真实结构：条目是组装出来的

拿一份真实成稿拆开看（[8年java开发-资深.md](../简历案例/8年java开发-资深.md) 个人能力第 1 条）：

> 【X】年搜索系统研发经验，精通 Elasticsearch / Lucene 内核与工程实践：倒排索引与段结构、BM25 相关性打分、近实时写入链路（refresh / Translog / flush）、分片规划与路由；主导搜索服务架构演进，具备写入与查询性能调优、深分页治理、大查询限流熔断的实战经验，并完成阿里云 ES 集群【版本升级 / 内核调优】（检索规模【N】亿级文档，QPS【X】，P99【X】ms）。

整条描述不可能写死——它因人而异。拆开后每一段都有固定的角色，个人的部分只是往角色里填内容：

| 段 | 文本 | 固定角色（可复用） | 个人部分（逐人不同） |
|---|---|---|---|
| 年限句 | 【X】年搜索系统研发经验 | 句式角色 | 年限数字 |
| 主张句 | 精通 ES / Lucene 内核与工程实践：倒排索引与段结构、BM25 … | 段型 + 强度词 + 子点列举骨架 | 强度拍板（写不写"精通"，写了就要扛住三层追问） |
| 实战句 | 主导搜索服务架构演进，具备 … 实战经验 | 动词句式角色 | 做没做过、主导还是参与 |
| 成果句 | 并完成阿里云 ES 集群【版本升级 / 内核调优】（规模 / QPS / P99） | 成果句式 + 选项槽 | 真实数字，每个数字背后要能讲出故事 |

这份简历文档自己已经把组装规则想了一半：动词强度 = 追问授权 = 复习投入等级（写「精通」的必须扛住追问三层）；映射不到复习章的主张从简历里删掉；【】占位符必须填真实且能讲出背后故事的数字。剩下的一半——段怎么拆、段之间怎么拼、拼的时候什么能跟什么放一起——就是本 PRD 要定的事。

用户判断作为需求起点：**每条技能是根据用户能力组装的，每个部分有固定角色，建档时组装成技能；组装必须守边界——Redis 不能和 JVM 优化放在一起**（两者分属存储与中间件、Java/JVM 两个域）。

### 1.2 现有设计的缺口

现行画像只有一张 user_skill（"定稿技能画像"）与一张域字典（核心模块定义 3.1），对照组装需求有三个缺口：

| 缺口 | 后果 |
|---|---|
| 画像条目没有结构：条目从哪来、长什么样没有契约 | 建档时 AI 现编整段条目，表述与强度不可控，也没有可逐项拍板的粒度 |
| 授权锚点太粗：授权按"条目 ↔ 域"关联 | 写了"ES 内核"等于授权整个搜索域的知识点——模拟考组卷权重 ×1.5 与简历主张存活率都锚在一个过大的范围上，失真 |
| 简历主张没有结构化承载 | 复盘的"练不住的主张从简历降级"只能作用于一段自由文本，降级降的是什么、降完简历长什么样，都说不清 |

### 1.3 简历使用原则的产品化

| 简历文件的三条使用原则 | 产品规则 |
|---|---|
| 动词强度 = 追问授权 = 复习投入等级 | 强度档四档（3.3），承诺深度 3 / 2 / 1 / 不入卷，驱动模拟考打穿基准与升降级建议（5.4 / 5.5） |
| 映射不到复习章的主张，从简历里删掉 | 主张项挂载知识库簇获得授权与验证锚点（3.5）；挂不上簇的主张合法保留但提示"无练习内容支撑"，且不进存活率定义域 |
| 【】数字必须真实且能讲出故事 | 数字槽 + 投递版校验（3.4 / 4.4）；数字背后的故事沉淀在建档项目素材（user_case），v1 不做强制关联 |

### 1.4 拍板记录：挂簇，不再建技能原子库（2026-09-23，决策清单 D26）

设计过程中曾提出"技能原子库"方案（skill 包新增原子模板表，B 端生产"标准简历话术"供用户认领，原子挂知识点作授权锚点）。该方案被否决，理由记录在案，防止将来摇摆：

1. **派生资产必然漂移**：原子挂知识点是第二份内容映射，知识库合并、下线知识点都要跟改原子，为此要引入上线校验、下线联动、待处理状态一整套机制。而簇本来就是知识库的内容组织单位，簇下知识点集合由知识库自己维护，挂载关系在消费时推导，零维护。
2. **库模板复用率撑不起生产成本**：简历主张是个人表达——实战段的动词与项目、成果段的数字、主张段的子点组合都因人而异，"标准话术"每个用户都要改，B 端生产它的租值很低。
3. **产品原意本来就是 LLM 起草 + 用户拍板**：核心模块定义 2.1 既定设计"AI 从简历和对话里整理出技能画像草案，用户逐条拍板"。产品提供骨架规范（段型、档位词表、槽位校验），不代写话术。

替代口径：**画像主张项直接挂载知识库簇**；库侧保留域字典（分组边界与排序），不新增任何内容表。

## 二、产品目标

| 目标 | 判定 |
|---|---|
| 建档组装可信：主张项由 LLM 对齐起草、用户逐条拍板 | 定稿画像中不存在用户未确认的主张；知识结构单一真相源在知识库，技能侧零内容资产 |
| 授权精确到簇：授权推导只走现成关系 | 授权 KP = 认领主张项挂载簇的成员 KP，不需要任何维护性映射表 |
| 简历可成稿：组装结果即简历能力区 | 定稿画像可按渲染规则一键复制 Markdown；升降级拍板后条目即时重渲染 |
| 主张可验证可练习：写了的主张背后有尺子 | 挂簇主张进存活率与组卷定义域；无簇主张显式警示、显式排除 |

## 三、核心概念与对象模型

### 3.1 技能域：隔离边界，条目的身份

域（skill_domain）维持现行设计（B 端维护、停用不删除、排序值决定建档候选与关卡组默认序），在本模型中承担两条语义：

- **域是组装的隔离边界**：主张项挂载的簇必须同域，条目单域组装，跨域主张永不同条目——Redis（存储与中间件域）与 JVM 调优（Java/JVM 域）不同条目。跨域的知识关联在学习侧用前置依赖表达（kp_prereq），不进简历条目。
- **条目 = 域的实例化**：简历"个人能力"区的一行对应一个域，条目标题即域名（"存储与中间件"）。有认领主张项的域才出条目。需要把一个条目拆成两条时，拆域（B 端运营动作），不引入"条目模板"层。

简历条目顺序独立于域排序：域排序值服务建档候选与关卡组默认序（全局资产语义），条目序是个人偏好（投搜索岗把搜索域提到最前——简历文档"两版简历"提醒的产品化），建档拍板时可调，默认跟域序。

### 3.2 技能条目与主张项

**条目**（user_skill）是域的个人实例；**主张项**（user_skill_item）是条目内可独立拍板去留、可独立升降级的最小单元，带段型、文本、强度档与挂载簇。

| 段型 | 语义 | 渲染句式 | 强度档 | 挂载簇 | 条目内数量 |
|---|---|---|---|---|---|
| summary 概览段 | 年限 / 定位陈述 | 陈述句，条目置顶 | 无 | 不挂 | ≤ 1 |
| claim 主张段 | 强度词统领的技术主张（原理 + 子点清单） | 强度句，同档聚合 | 必填 | ≥ 1 推荐 | 不限 |
| practice 实战段 | 做过的事，动词开头（主导 / 建设 / 治理） | 动词句，同档聚合 | 必填 | ≥ 1 推荐 | 不限 |
| result 成果段 | 做成的事 + 数字 | 成果句，逐条 | 必填 | 推荐挂 | 不限 |
| quality 素养段 | 协作 / 带教 / 工程素养 | 陈述句聚合 | 无 | 不挂 | 不限 |

- **主张项文本是个人表达**：由建档 LLM 对简历主张与对话内容起草，用户拍板确认后定稿——库侧没有文本模板，只有段型骨架与渲染词表（3.3）。
- **粒度判据**：一次拍板能决定去留、一次升降级能落到它头上。主张句里的子点列举（"倒排索引与段结构、BM25 …"）是主张项文本的一部分，不拆；若某半句经常被单独争议，用户自行拆成两条主张项。
- **条件钩子拆主张项**：简历文档里"【+ 向量召回：做了才保留】"这类钩子不存在于模型中——需要条件保留的主张就是一条独立主张项，认领与否就是钩子本身。主张项文本内保留的只有选项槽（3.4 的 A|B 二选一）。

### 3.3 强度档位：四档承诺

强度档（claim_level）是**主张项**的属性（claim / practice / result 必填，建档拍板时定）。四档定义：

| 档位 | 渲染词表 | 承诺层 | 语义 |
|---|---|---|---|
| expert | 精通 | 3 层 | 被问穿第 3 层即视为主张被打穿，触发降档建议 |
| proficient | 熟练使用 / 扎实掌握 / 掌握 | 2 层 | 同上，基准第 2 层 |
| familiar | 熟悉 / 理解 | 1 层 | 盲测通过即可守住的主张 |
| aware | 了解 | 0（不入卷） | 不进模拟考组卷与存活率定义域，练习闪卡照常可见 |

拍板记录（2026-09-23）：简历原文六种动词归并为四档——档位是模型概念，简历措辞靠渲染词表还原；具体措辞在拍板时从词表内选，默认取首选词。practice 段的强度体现在主张项文本的动词上（"主导…"对"参与…"），档位对它只驱动承诺深度与排序，渲染时不再叠加强度词。

**档位与职级停止点的关系**：职级停止点是库侧尺子（目标职级答到第 N 层算过关），强度档是主张的承诺（简历上写了这个强度，面试官就会问这么深）。两者正交，消费处合成"有效停止点"（5.4）。

### 3.4 槽位

| 槽型 | 写法（示意） | 填充 |
|---|---|---|
| 数字槽 | {years}、{qps}、{p99}、{doc_scale} | 用户建档时填真实值，渲染时替换；未填渲染为【待填】 |
| 选项槽 | [版本升级\|内核调优] | 二选一，拍板时选定 |

约束：槽位值随主张项保存（JSON）；槽位值为文本，v1 不做数字类型校验——真实性靠建档对话与拍板把关（原则 3 的故事在 user_case 沉淀）。槽位占位符的具体语法（`{}` / `[]`）实现期定，PRD 锁语义不锁字符。

### 3.5 挂载簇：授权锚点

- 主张项挂载的是**知识库主题簇**（kp_cluster），不直接挂知识点、不建独立映射资产。挂簇即授权该簇全部成员知识点（kp_main 挂且只挂一个主簇，成员关系现成）——授权推导零维护（1.4 拍板的直接落点）。
- 一个主张项可挂多个簇（"ES 内核与工程实践"覆盖倒排、打分、写入、分片多簇）；**挂载限同域**：簇的域必须一致，且决定该主张项所属条目——域隔离的校验点在挂载上。
- 挂载为多对多（user_skill_item_cluster）；cluster_id 是逻辑引用、不做外键（跨包先例同 answer_log.attempt_id）。必须支持按簇反查主张项（索引关系表）——升降级建议依赖反向查找。
- **无簇可挂的主张合法**：知识库没有对应内容（小众技术栈、超纲主张）时，主张项可挂 0 簇保留。建档预览提示"该主张无对应练习内容，被问穿风险高"，且不进授权、组卷与存活率定义域（没有尺子就无法判存活）。产品不拦用户写简历，只负责让写了的主张可验证、可练习；复盘录题回流是这类主张的内容兜底。
- v1 只挂簇不直挂知识点（拍板）：簇粒度即主题粒度，直挂知识点会让建档拍板负担陡增；多授权的代价只是多练几题，符合并集准入原则（核心模块定义 2.2），漏授权才是结构性风险。

## 四、组装规则与简历渲染

### 4.1 三条硬规则

1. **域隔离**：条目单域组装；主张项挂载簇同域，跨域主张永不同条目（1.1 需求起点的直接落点）。
2. **一域一条目**：条目 = 域实例化，无认领主张项则无条目（简历不写该域）。
3. **渲染是确定性代码**：组装与渲染不含任何 LLM 调用——简历成稿是骨架拼装，一个字都不让模型编。LLM 只出现在建档整理环节（5.1），且只做对齐与起草，成稿文本必经用户拍板。

### 4.2 条目组装骨架

条目内主张项的渲染顺序固定：

```
summary（至多 1 条）
→ claim：按档位 expert → proficient → familiar → aware 降序，同档聚合为一个强度句，档内按排序值
→ practice：按档位降序，同档聚合为一个动词句，档内按排序值
→ result：逐条成句，按排序值
→ quality：聚合为一个陈述句，按排序值
```

claim 聚合句式：`{档位渲染词} {主张项1}、{主张项2}…`（同档多主张共享一个强度词——对应简历原文"熟练使用 MySQL …、Redis …、RocketMQ …"的形态）；practice 聚合句式：主张项文本自带动词开头，句间用分号；result 段每条独立成句，数字槽填充。

### 4.3 渲染示例

搜索域条目的一次拍板结果：

| # | 段型 | 主张文本（用户确认后） | 档位 | 挂载簇（示意） |
|---|---|---|---|---|
| a1 | summary | 8 年搜索系统研发经验 | — | — |
| a2 | claim | Elasticsearch / Lucene 内核与工程实践：倒排索引与段结构、BM25 相关性打分、近实时写入链路（refresh / Translog / flush）、分片规划与路由 | expert | 倒排索引与段、相关性打分、近实时写入、分片规划与路由 |
| a3 | claim | BM25 + 向量混合检索与 rerank 精排 | familiar | 混合检索与 rerank |
| a4 | practice | 主导搜索服务架构演进，具备写入与查询性能调优、深分页治理、大查询限流熔断的实战经验 | proficient | 深分页治理、限流熔断降级 |
| a5 | result | 完成阿里云 ES 集群[版本升级\|内核调优]（检索规模 {doc_scale}，QPS {qps}，P99 {p99} ms） | proficient | ES 集群运维 |

渲染结果（即简历能力区该条目的成品，a3 若用户不认领则不出现）：

> 8 年搜索系统研发经验，精通 Elasticsearch / Lucene 内核与工程实践：倒排索引与段结构、BM25 相关性打分、近实时写入链路（refresh / Translog / flush）、分片规划与路由；主导搜索服务架构演进，具备写入与查询性能调优、深分页治理、大查询限流熔断的实战经验；完成阿里云 ES 集群版本升级（检索规模 3 亿，QPS 8000，P99 200 ms）。

强度词由档位注入（a2 文本不含"精通"二字）、数字来自槽位填充、挂载簇决定了这批主张背后有哪些可练的内容——这就是"角色固化、按人组装"的完整闭环。

### 4.4 投递版校验

- result 段数字槽未填满的条目，渲染时标【待填】并阻断"复制投递版"——占位符清单不填完不算成稿（简历文档既有规则）；复习版不受限。
- 除数字槽外不做其他阻断；aware 档主张照常渲染（写不写"了解"是用户对自己简历的判断），提示只出现在建档拍板界面。

## 五、C 端消费契约

### 5.1 建档组装流程

建档（profile，T10）消费域字典与知识库簇树，流程与职责边界如下：

1. **输入**：简历解析文本（docparse）+ 建档对话收集（年限 / 岗位 / 技术栈 / 项目）。
2. **对齐参照**：域 → 簇树（active 簇及簇下知识点题面样本，经 kb 只读接口获取）——LLM 对齐的参照物就是知识库现成的分类体系，技能侧不提供第二份候选清单。
3. **LLM 整理**（低频必要类限额入口，沿用 4.2 成本治理）：任务限定为四件——把简历主张对齐到簇（含匹配度）、起草主张项文本（按段型句式规范，prompt 模板归 profile 包 resources，判定模板归 judge 的同款先例）、推测建议档、抽取槽位填充值。**LLM 不定档、不定稿**：它搬运、对齐、起稿，事实、强度与措辞由用户逐条拍板（核心模块定义 2.1 既有原则）。
4. **候选清单**：按域分组展示主张项候选，每条含匹配来源（简历原文引用）、建议档、建议挂载簇、槽位预填值。
5. **用户拍板（主张项级）**：认领 / 不认领 / 改档 / 改措辞 / 调整挂载簇 / 填槽位 / 调序；挂载簇可从建议改选同域其他簇，也可清空（触发"无练习内容支撑"警示）。
6. **组装预览**：按第四渲染规则实时预览条目，所见即所得。
7. **定稿**：随画像状态机（草稿 → 确认 → 定稿，2.1 既有）；定稿后授权锚点生效。
8. **空域合法**：某域没有认领主张项即不出条目，不强制凑满。

### 5.2 授权锚点口径修订

核心模块定义 2.2 的授权推导口径由"条目经域关联知识点"修订为：

> 知识点 K 对档案 P 简历授权 = P 定稿画像中存在主张项挂载 K 的主簇。

- aware 档主张项挂载的簇同样进学习关卡（弱主张不等于不学——2.2"画像条目删除的语义是修正真实水平"的同一逻辑），但不进模拟考授权权重（×1.5）与存活率定义域。
- 挂 0 簇的主张项不产生授权（3.5）。
- 域从授权推导中退位：域只承担组织边界（条目、关卡组归属、挂载约束），不再充当授权的匹配键。

### 5.3 强度承诺与打穿基准

简历文档的原则 1（写精通就要扛三层）是真实面试行为，把它合成进模拟考：

- **有效停止点 = min(该题最大追问层， max(职级停止点， 承诺层))**，承诺层按主张项档位取 3 / 2 / 1（aware 不参与）。
- 模拟考逐问判定的下钻范围以有效停止点为界；"主张被打穿" = 未扛住有效停止点。
- 组卷抽中权重 ∝ 简历授权（×1.5 既有） × 强度因子（expert 1.3 / proficient 1.1 / familiar 1.0；aware 不入卷），因子为默认值、配置化（企划书"参数放配置"的既有口径）。
- 生成关卡的排序规则不变（组内难度与前置拓扑既有）——强度档管"考多深"，不管"学什么先"。

### 5.4 升降级建议

复盘（2.6）与模拟考存活率的建议载体由"简历主张"细化为**主张项**：

- **降级**：某知识点被打穿 → 该知识点的主簇 → 反查挂载该簇的主张项 → 建议档位下调（expert → proficient → familiar → aware → 撤除）。
- **升级**：某知识点连续扛住深问或复盘录题答上 → 建议档位上调，或建议把该知识点的主簇挂进认领主张项（"练深了的知识点写成简历亮点"的落点）。
- 建议结构：`{主张项, 动作(下调/上调/撤除/补挂簇), 现档, 建议档, 依据(判定或信号引用)}`，走 profile api（exam → profile 依赖既有），**用户拍板后才改 user_skill_item**——建议不落改，简历永远是用户的。
- 档案级"连续两场存活率低于 50% 自动触发降级建议"保留（2.5 既有），主张项级建议是它的细化。

### 5.5 画像即简历预览

定稿画像页按渲染规则展示各域条目，提供"复制能力区 Markdown"动作（4.4 校验通过为前提）；升降级拍板保存后条目即时重渲染。完整简历导出（项目经历、教育背景、排版与文件格式）在范围外（第八节）。

## 六、B 端与知识库侧的配套口径

- **B 端不新增页面**：技能库页（/admin/skills）维持域字典管理详设（[B端管理台PRD](B端管理台PRD.md) 第四节：列表 / 新增 / 编辑 / 排序 / 停用不删除 / 空字典前置引导），无改动、无新表。
- **簇作为挂载对象的两条软约束**（知识库内容生产的既有节奏内消化，不新增校验机制）：
  1. 簇名面向主题命名（"近实时写入"而非"refreshTranslog详解"）——簇名是对齐参照物与升降级建议的展示单元，可读性影响建档对齐质量与用户拍板效率。
  2. 一个簇 ≈ 一个可独立主张的主题——簇粒度过粗（一个簇半个技能域）会让授权失真，过碎（一簇一题）会让拍板负担陡增。人工校对清单（知识库PRD 八）复核簇切分时，顺带按这两条目检即可，不新增检查项。
- **知识库PRD 不因本文改动**：挂载是态侧消费，簇的库侧语义（生产单位、状态机、从零讲）不变，仅新增一类只读消费方。

## 十、落地与验收

### 10.1 任务落位

- **T3 技能库**：范围不变（skill_domain 建表 + B 端域管理 + SkillsView 接线），验收沿用 B端管理台PRD 十四。
- **T10 建档**：消费本 PRD 全部契约——域字典与簇树对齐、主张项拍板与组装预览、渲染与投递版校验、授权推导、升降级建议读写。
- 无新增独立任务（原设想的"原子库"任务取消，见 1.4）。

### 10.2 T10 组装链路验收清单

1. 拍板闭环：LLM 起草的主张项全部经用户拍板后才能定稿；定稿画像中不存在未确认主张。
2. 挂载校验：跨域簇挂载被拒绝（可读中文错误）；挂 0 簇的 claim 主张触发"无练习内容支撑"警示且不进授权。
3. 授权推导：挂载簇的成员知识点全部进授权定义域；aware 档主张项挂载的知识点进学习关卡、不进模拟考组卷。
4. 渲染：段型序 + 档位降序聚合 + 槽位填充 + 【待填】阻断投递版；与 4.3 示例一致。
5. 升降级：打穿知识点 → 主簇 → 反查主张项 → 建议落点正确；用户拍板前画像数据不变。
6. `mvn test` 绿 + `npm run build` 绿。

### 10.3 一句话收束

知识结构只有知识库一份，简历表达只有用户一份：建档把两边对上——主张项挂簇，写了的可练、练不住的降、练深了的升；简历和知识库互相改，从此有了一个可操作的载体。
